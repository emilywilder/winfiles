# Testing

The Pester tests and their fakes, `demos/`, and the test VM.

`just test` (`scripts/Invoke-Tests.ps1`, through `Invoke-Clean.ps1`) runs the Pester tests in `tests/`: `tests/resources/` for the `Winfiles/*` resources and `tests/scripts/` for the scripts. Pester is a module, which mise can't install, so the script pins its version (6.2.0), saves it to `~/.cache/winfiles/modules` on first use and imports it from there. The tests cover what a resource decides, such as carrying on past a package that fails and still exiting 0, which exit codes it uses, and the JSON and messages it writes. They don't cover how Windows, winget or an installer behaves, which is what the test VM has caught so far. `tests/resources/Resource.ps1`'s `Invoke-Resource` runs a resource as DSC does: a child pwsh started with the command from its manifest, in `dsc/resources`, with the instance on stdin. What it talks to is replaced with fakes made of files in `tests/fakes`, not with Pester mocks: a `Microsoft.WinGet.Client` module put first on the child's `PSModulePath`, with its state in a JSON file, and a `scoop.ps1` in a temporary Scoop root that `$env:SCOOP` points to, which leaves the same files real Scoop does. `Winfiles/Scoop` downloads `tests/fakes/scoop-install.ps1` from `Start-FakeWebServer`, a `TcpListener` on a free loopback port (`Invoke-WebRequest` has no `file://`, and an `HttpListener` would need elevation). Its install tests only run unelevated, and the test of refusing elevation only runs elevated, so an elevated `just test` skips the rest. `Assert-FakeWinGetLoads` stops the winget tests if a child pwsh would load the real module, and the fake throws without its state file, so a test can't install real packages. `Winfiles/WslDistribution` is the exception: it names its registry keys, its CIM class and `wsl.exe` itself, which a child process can't be pointed away from, so `Invoke-ResourceScript` runs its script in the test's process with Pester mocks. The fake machine is still real where it can be: default mocks of `Test-Path`, `Get-ItemProperty` and `Get-ChildItem` rewrite the `Lxss` and `RebootPending` paths to Pester's `TestRegistry:` (Pester 6 has no fallthrough for a mock whose filters don't match, so they're defaults that call the cmdlet through its CommandInfo, which a mock can't intercept), the fake `wsl.exe` registers what it installs there, and sources are files in `TestDrive:`. Trade-off: those tests run in about 0.1s each but don't cover the manifest; revisit if the script gains seams a child process could use. Trade-off: about 0.6s per test for a child pwsh, for tests that also cover the manifest and the real stdin, stderr and exit codes. Revisit if the suite gets slow enough to skip. Keep the fakes basic: extend one when a test needs it, rather than modelling Windows.
The script tests run each script in a child pwsh with `Invoke-Script`, with `USERPROFILE` (which pwsh's `$HOME` follows) pointed into `TestDrive:` wherever a script writes under `~`. `tests/fakes/bin` holds `dsc.cmd` and `winget.cmd`, put first on the child's `PATH`: the fake `dsc` answers each `--file` from canned JSON, so `Test-Winfiles.ps1`, `Set-Winfiles.ps1`, `dsclog.ps1` and `Invoke-Dsc.ps1` run for real against it, and the fake `winget` records `Get-ManualInstaller.ps1`'s downloads without making them. `Get-ManualInstaller.ps1` reads the real Uninstall keys, without writing them, so its tests name a program installed on the machine and ones that can't be. Not tested: the scripts that need a test VM or elevation (`New-TestVm.ps1`, `Copy-RepoToTestVm.ps1`, `Enter-TestVm.ps1`, `testvm.ps1`) and `Export-DscResource.ps1`, a nice-to-have. `Install-Wsl.ps1` names its CIM classes, registry key and `wsl.exe` itself, elevates and restarts Windows, so like `Winfiles/WslDistribution` it runs in the test's process with Pester mocks, against a fake WSL held in a hashtable that `--install` and `--update` change. `install.cmd`'s tests run it for real (so it writes the RunOnce entry, and removes it when `require` fails), with this machine's mise and just, but only with a host that has no configuration, so `just install` stops in `require` before UAC or any change; they cover its arguments, exit code, working folder and clean environment. `Invoke-Install.ps1`'s tests run a copy of it under Windows PowerShell 5.1 with a fake `Start-Clean.ps1`, and a RunOnce key of their own under HKCU (the script's `-RunOnceKey`), never the real one. Its tests also cover that the entry is written before the run (a restart during it can't beat it), that the key's other values survive, and that a newer entry replaces an older one. `Resume-Winfiles.ps1`'s tests run a copy of it under Windows PowerShell 5.1 with a fake `install.cmd`, a restart-pending key of their own under HKCU and a `TcpListener` on loopback standing in for winget's source (the script's `-RebootPendingKey`, `-SourceHost`, `-SourcePort` and `-WaitSeconds`). They cover the arguments passed on, the move to the repo (RunOnce starts it in System32), the exit code reported, stopping on a pending restart, and going ahead after the wait when the source can't be reached. One test chains the real `Invoke-Install.ps1` and `Resume-Winfiles.ps1` through two restarts, deleting the RunOnce value between runs as Windows does. Not tested: that the RunOnce entry fires at the next sign-in, that its `cmd /c start` window stays open, and that the restart's exit code reaches `Invoke-Install.ps1` through `just`, `mise exec`, `Invoke-Clean.ps1` and `Start-Clean.ps1`. They need a real restart in the test VM, where a full run resumed correctly (checked 2026-11-16; see `docs/install.md`). `Invoke-Clean.ps1`'s tests run commands under the real mise, since the environment it builds comes from Windows, which also leaves a missing mise untested; they run its version check under Windows PowerShell 5.1, the older version at hand. `Start-Clean.ps1` is tested under 5.1 with a `PATH` that has no mise, and with the real one, but its missing-mise exit isn't, since the registry's `PATH` can't be faked. The choice of mise configuration to ignore (`miseignore.ps1`) is tested under pwsh 7 and under Windows PowerShell 5.1, which `Start-Clean.ps1` runs it in, and against this machine's `mise config ls --json`, to check that mise spells the repo's `mise.toml` the way the script compares it. `Initialize-Winfiles.ps1`'s tests cover its checks and what it prints, not its installs: past the checks it changes the machine, so a test that got that far would install real packages. `bootstrap.cmd`'s test runs it from a copy of the repo without `mise.toml`, so the checks stop it the same way. Each `.cmd` in the repo root is checked for CRLF line endings and a `.gitattributes` entry, since cmd.exe misreads LF. Trade-off: a fake `dsc` call starts `cmd` and pwsh, about 2s a test with `Invoke-Dsc.ps1`'s own `Get-AppxPackage`, for tests that run the scripts' real path to dsc.

`demos/` holds things run by hand to watch how something behaves, with nothing to pass or fail, kept apart from the tests in `tests/`. Their recipes are in `demos/justfile`, not the main one: run `just <recipe>` from `demos/`, or `just -f demos/justfile <recipe>` from the root. `demos/dsc-messages/` (`just dsc-messages <doc> [dsc args]`) is a visual check of how DSC shows lines a resource writes to stderr (levels, live output, Include nesting). Its README records the results per DSC version. Its stand-in resource `Test/SlowList` is outside `dsc/resources`, so `just dsc` never discovers it.

A test VM's computer name doesn't decide its configuration, so pass the host: `.\install.cmd vm`.
For a quick run, use the `vm-quick` host (`.\install.cmd vm-quick`). It goes through every step of `just install` (features, WSL, both configurations, `check`, `post-install`) and every kind of resource, with the shared modules that configure rather than install included as they are. The package lists are replaced by a few small packages in `dsc/hosts/vm-quick/`, chosen so each list still takes its paths: one already installed, one to install machine-wide, one per user, a bare Scoop name and a `bucket/name`. The home entry passes `parametersContent` to the `modules/home/wsl.dsc.yaml` Include, which puts a pinned Alpine minirootfs in place of NixOS-WSL (`wsl --install --from-file` takes its `.tar.gz`: installed through `Winfiles/WslDistribution` with its sha256 on iris, 2026-11-15). Every Scoop bucket is still added. Its `# post-install:` note is the reminder of what it leaves out. Trade-off: a package that only fails in the real lists, or a NixOS-WSL image problem, only shows up under `vm`, so run `vm` before relying on a change to either. Revisit if the two drift, for example when a shared module gains an install that `vm-quick` doesn't cover. Test a clean install in that VM, not in Windows Sandbox: the Sandbox doesn't expose virtualization to its guest, so WSL2 can't run there, and it has no Store or winget. The script creates the VM and doesn't start it. It fixes the screen at 1920×1080 for basic `vmconnect` sessions (the VM's own console); an enhanced session (Remote Desktop over VMBus, with a shared clipboard) sizes it to the window. It prints the `Checkpoint-VM` and `Restore-VMCheckpoint` commands for taking a `clean` checkpoint after Windows setup and returning to it. Without `-Unattended` the VM boots the ISO into Windows Setup. With it, Setup is skipped: the script applies `Windows 11 Pro` from the ISO to the VHDX, runs `bcdboot`, and writes `Windows\Panther\unattend.xml`, which answers OOBE, creates a local administrator named after you, and signs it in automatically at every boot, so the install's restart needs no attention. The administrator's password is blank, and the specialize pass sets `LimitBlankPasswordUse` to 0, which by default limits blank passwords to the console. So a basic session opens on the desktop, an enhanced session signs in with one click on **Sign in**, and PowerShell Direct needs no password; a restart comes back by itself in either session (checked 2026-10-29 on 26300). The VM's notes record the administrator (`Local administrator: <user> / `, with nothing after the slash), and `scripts/testvm.ps1` reads them for the PowerShell Direct scripts. Trade-off: a blank-password administrator that accepts remote sign-ins, acceptable only because the VM is a throwaway behind the Default Switch's NAT; never do this on a real machine. It replaced a generated password kept in the notes, which every sign-in through an enhanced session made you type. The VM has no sleep states (`powercfg /a`), so it never asks to sign in on wake. The computer name defaults to the VM name, and Setup rejects one longer than 15 characters at first boot, so the script checks it up front; pass `-ComputerName` for a longer `-Name`. The VM stays unactivated, which doesn't affect winfiles.
`just test-vm-copy` packs the repo with `git archive` (by default the working tree: commits plus uncommitted changes to tracked files, through `git stash create`; untracked files are left out) and copies it in over PowerShell Direct, signing in with the administrator from the VM's notes (`-Credential` for a VM installed by hand). It replaces `~\src\winfiles` in the VM, so edits made inside the VM are lost.
PowerShell Direct sessions run elevated with no UAC, so run `bootstrap.cmd` and `install.cmd` in the VM's desktop, and keep `test-vm-shell`, `test-vm-run` and `test-vm-log` for reading results, such as `just test-vm-run <name> 'mise exec -- just check vm'`. Under them, Scoop's installer would refuse to run and the gsudo prompt would never show.
`just test-vm-log` follows winget's `DiagOutputDir` in the VM, the only logs a run writes while it's going. Each package adds files there, and the COM log and an installer's log are active at once, so it follows every `*.log` written to since a minute before it started, polling every 2s, with a header when the output moves to another file. It keeps a byte offset per file, so a large MSI log isn't reread, but it opens each followed file on every poll, because a directory listing can lag behind a writer that keeps its handle open. The encoding comes from each file's byte order mark (UTF-16 either way, or UTF-8 with or without one), and a file that existed before the start shows its last `-Tail` lines, read from its last 64KB only. Its watch scriptblock runs under Windows PowerShell 5.1 in the VM, so it has to stay compatible, and PowerShell Direct sends only the scriptblock, so the functions it uses are defined inside it rather than at the script's top level. The scriptblock takes the folder as `-Directory` and a number of polls as `-Polls` (0, the default, follows until the session ends), so `tests/scripts/Watch-TestVmLog.Tests.ps1` runs it without a VM: it takes `$watch` from the script's AST, runs it under `powershell.exe` against scratch logs, and covers the four encodings, the 64KB tail of a large UTF-16 file, a line split across two writes and the header at each move between files (a mutation that stopped skipping the cut line failed the large-file test, 2026-11-16). The default folder has a wildcard in the middle of its path, which makes `Get-ChildItem` list the matching folder itself rather than its files, so the script resolves the path first; a test with a wildcard path covers that (it was missed while every test passed a literal folder, and the watch showed nothing in a real run, 2026-11-16). The two tests that write between polls start the process and wait about 2s for the second poll. The host side, `Get-VM` and the reconnect, needs a running VM. A VM that isn't running fails with a message; once following, a guest restart reconnects and a stopped VM ends it. Trade-offs: Scoop, DSC and `wsl --install` don't write there, so those parts of a run look idle; a line with no line ending yet stays hidden until it gets one; and it asks for UAC, because `Get-VM` is denied otherwise (checked on iris, where the user isn't in Hyper-V Administrators). It's outside the run, so a run needs no change to be followed. Revisit if the Scoop or DSC gap gets in the way, which a stable log written by `Write-ResourceMessage` could fill, or if the UAC prompt becomes a nuisance.
