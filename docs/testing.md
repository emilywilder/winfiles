# Testing

The Pester tests and their fakes, `demos/`, `surveys/`, and the test VM.

`just test` (`scripts/Invoke-Tests.ps1`, through `Invoke-Clean.ps1`) runs the Pester tests in `tests/`: `tests/resources/` for the `Winfiles/*` resources and `tests/scripts/` for the scripts. Pester is a module, which mise can't install, so the script pins its version (6.2.0), saves it to `~/.cache/winfiles/modules` on first use and imports it from there. The tests cover what a resource decides, such as carrying on past a package that fails and still exiting 0, which exit codes it uses, and the JSON and messages it writes. They don't cover how Windows, winget or an installer behaves, which is what the test VM has caught so far. `tests/resources/Resource.ps1`'s `Invoke-Resource` runs a resource as DSC does: a child pwsh started with the command from its manifest, in `dsc/resources`, with the instance on stdin. What it talks to is replaced with fakes made of files in `tests/fakes`, not with Pester mocks: a `winget` (`tests/fakes/bin/winget.cmd`, below) put first on the child's `PATH`, with its state in a folder, and a `scoop.ps1` in a temporary Scoop root that `$env:SCOOP` points to, which leaves the same files real Scoop does. `Winfiles/Scoop` downloads `tests/fakes/scoop-install.ps1` from `Start-FakeWebServer`, a `TcpListener` on a free loopback port (`Invoke-WebRequest` has no `file://`, and an `HttpListener` would need elevation). Its install tests only run unelevated, and the test of refusing elevation only runs elevated, so an elevated `just test` skips the rest. The fake `winget` throws without its state folder, and `Assert-FakeWinGetCliRuns` stops the winget tests if a child pwsh would find the real one first, so a test can't install real packages. `Winfiles/WslDistribution` is the exception: it names its registry keys, its CIM class and `wsl.exe` itself, which a child process can't be pointed away from, so `Invoke-ResourceScript` runs its script in the test's process with Pester mocks. The fake machine is still real where it can be: default mocks of `Test-Path`, `Get-ItemProperty` and `Get-ChildItem` rewrite the `Lxss` and `RebootPending` paths to Pester's `TestRegistry:` (Pester 6 has no fallthrough for a mock whose filters don't match, so they're defaults that call the cmdlet through its CommandInfo, which a mock can't intercept), the fake `wsl.exe` registers what it installs there, and sources are files in `TestDrive:`. Trade-off: those tests run in about 0.1s each but don't cover the manifest; revisit if the script gains seams a child process could use. Trade-off: about 0.6s per test for a child pwsh, for tests that also cover the manifest and the real stdin, stderr and exit codes. Revisit if the suite gets slow enough to skip. A resource that reports `_restartRequired` has its entries checked against DSC's own schema (`Assert-RestartRequiredSchema` in `Resource.ps1`, from `dsc schema -t restart-required`), because DSC 3.3.0 only logs a warning for an entry that doesn't fit and the restart then goes unreported (checked 2026-11-18). The test needs the pinned `dsc` on `PATH`, so it fails, rather than skips, when run outside `just test`. Keep the fakes basic: extend one when a test needs it, rather than modelling Windows.
The script tests run each script in a child pwsh with `Invoke-Script`, with `USERPROFILE` (which pwsh's `$HOME` follows) pointed into `TestDrive:` wherever a script writes under `~`. `tests/fakes/bin` holds `dsc.cmd`, `winget.cmd` and `gsudo.cmd`, put first on the child's `PATH` (the fake `gsudo` writes its arguments to a file and runs nothing, so `Invoke-AsAdmin.ps1` and `Invoke-AsUser.ps1`'s tests never elevate; it is first on `PATH` as well as passed in, because a script that ignored the override once reached the real gsudo, 2026-11-18): the fake `dsc` answers each `--file` from canned JSON, so `Test-Winfiles.ps1`, `Set-Winfiles.ps1`, `dsclog.ps1` and `Invoke-Dsc.ps1` run for real against it, and the fake `winget` (`fake-winget.ps1`, behind `winget.cmd`) records `Get-ManualInstaller.ps1`'s downloads without making them. `ConvertTo-FlatConfiguration.ps1` runs the real `yq` from `mise.toml` on small documents written to `TestDrive:` (each refusal has a test), and on every entry document in `dsc/`, so a resource or parameter name used twice across modules fails `just test` rather than the start of an install; its tests also read the recipes with `just --dry-run`, to check that `install-steps` runs `Invoke-Configuration.ps1` on the system and home documents together and that `flat=false` is gone, and run `just flatten` on a missing document for its exit code (only the failure, since a flat copy that succeeds goes to the real `~/.local/state`, which `Invoke-Clean.ps1` restores whatever `USERPROFILE` the test sets). The tests of `Test-Winfiles.ps1` and `Set-Winfiles.ps1` write a small flat document, which the fake `dsc` answers by file name, and one with an Include, which they must refuse (`ConvertTo-FlatConfiguration.Tests.ps1` flattens the real system and home documents); that the flat copy of a real entry gives the same results as the entry is checked by hand with `config test` (`docs/benchmarks.md`, "check"). The same fake runs `Winfiles.WinGet/Package`'s tests: it answers `winget dscv3 package` from a list of installed ids, printing what winget 1.29.380's did, and `install` adds to that list. `Get-ManualInstaller.ps1` reads the real Uninstall keys, without writing them, so its tests name a program installed on the machine and ones that can't be. Not tested: the scripts that need a test VM or elevation (`New-TestVm.ps1`, `Copy-RepoToTestVm.ps1`, `Enter-TestVm.ps1`, `testvm.ps1`) and `Export-DscResource.ps1`, a nice-to-have. `Winfiles/Wsl` and `Winfiles/ComputerName` name their CIM classes, registry keys, `wsl.exe` and `whoami.exe` themselves, so like `Winfiles/WslDistribution` they run in the test's process with Pester mocks, `Winfiles/Wsl` against a fake WSL held in a hashtable that `--install` and `--update` change; elevation is read through `whoami.exe /groups` so a test can mock it. `Invoke-Configuration.ps1`'s tests run it in a child process with the fake `dsc` and fake `gsudo` and `WINFILES_ELEVATED=true`, so no test elevates: they check the batches it runs and in which order, that a resource reporting `_restartRequired` in the fake `dsc`'s `test` answer is pulled forward into a first batch of the `restart` stage (and that nothing is when none reports one), and the one total of a `test`. What Windows says about a pending restart is the real machine's, which a child can't mock, so the restart gate itself (the end of `Set-RestartStage.ps1`, and the check after each batch) is not tested; before 2026-11-19 `Set-System.ps1`'s tests mocked it in-process, and they went with the script, so that is a loss (`docs/optional-goals.md` has a way back: a seam for `Test-BlockingRestartPending`). What doesn't depend on the machine is tested (2026-11-19): `Set-RestartStage.Tests.ps1` checks which dsc operations it runs and in what order, what it tells the person before applying, and its failures and refusals, with exit codes of 0 or 3010 since the machine decides (nothing in them can make a restart pending, so none starts one); `Find-RestartResources.Tests.ps1` checks the `winfiles-restart:` lines, a resource inside an Include result, an empty answer and a failed test; and `Invoke-Configuration.Tests.ps1` also covers 194 logged as a stop for a restart and a failed discovery stopping the run before anything is applied. `Test-Winfiles.ps1`'s `-TotalsFile` and `Set-Winfiles.ps1`'s `apply` phase for a batch name are in their own tests. `restart.ps1`'s tests fake only the servicing key and the computer's two names. `dsclog.Tests.ps1` runs `Get-ResourceResult`, `Get-RestartReport` and `Get-ResourceProblem` on the result shapes DSC 3.3.0 gives (a resource on its own, and inside an Include after a `test` and after a `set`), since `Get-RestartReport` is what tells the person, before anything is applied, which resource will need a restart. Not tested: running the features for real, which needs an elevated shell (`Microsoft.Windows/OptionalFeatureList` fails unelevated even for `test`), and what DSC reports for that resource's `set` when no restart is needed (as of 2026-11-18). `install.cmd`'s tests run it for real (so it writes the RunOnce entry, and removes it when `require` fails), with this machine's mise and just, but only with a host that has no configuration, so `just install` stops in `require` before UAC or any change; they cover its arguments, exit code, working folder and clean environment. `Invoke-Install.ps1`'s tests run a copy of it under Windows PowerShell 5.1 with a fake `Start-Clean.ps1`, and a RunOnce key of their own under HKCU (the script's `-RunOnceKey`), never the real one. Its tests also cover that the entry is written before the run (a restart during it can't beat it), that the key's other values survive, and that a newer entry replaces an older one. `Resume-Winfiles.ps1`'s tests run a copy of it under Windows PowerShell 5.1 with a fake `install.cmd`, a restart-pending key of their own under HKCU and a `TcpListener` on loopback standing in for winget's source (the script's `-RebootPendingKey`, `-SourceHost`, `-SourcePort` and `-WaitSeconds`). They cover the arguments passed on, the move to the repo (RunOnce starts it in System32), the exit code reported, stopping on a pending restart, and going ahead after the wait when the source can't be reached. One test chains the real `Invoke-Install.ps1` and `Resume-Winfiles.ps1` through two restarts, deleting the RunOnce value between runs as Windows does. Both scripts' tests, and the chain's, also check the `[resume]` lines they write to `run.log`, with `USERPROFILE` pointed into `TestDrive:`; `install.cmd`'s tests point it there too, so `Invoke-Install.ps1` never writes the real log (the run itself gets the real profile back from `Invoke-Clean.ps1`). Not tested: that the RunOnce entry fires at the next sign-in, that its `cmd /c start` window stays open, and that the restart's exit code reaches `Invoke-Install.ps1` through `just`, `mise exec`, `Invoke-Clean.ps1` and `Start-Clean.ps1`. They need a real restart in the test VM, where a full run resumed correctly (checked 2026-11-16; see `docs/reference/test-vm.md`). `Invoke-Clean.ps1`'s tests run commands under the real mise, since the environment it builds comes from Windows, which also leaves a missing mise untested; they run its version check under Windows PowerShell 5.1, the older version at hand. `Start-Clean.ps1` is tested under 5.1 with a `PATH` that has no mise, and with the real one, but its missing-mise exit isn't, since the registry's `PATH` can't be faked. The choice of mise configuration to ignore (`miseignore.ps1`) is tested under pwsh 7 and under Windows PowerShell 5.1, which `Start-Clean.ps1` runs it in, and against this machine's `mise config ls --json`, to check that mise spells the repo's `mise.toml` the way the script compares it. `Initialize-Winfiles.ps1`'s tests cover its checks and what it prints, not its installs: past the checks it changes the machine, so a test that got that far would install real packages. The one exception is the failure of the App Installer retry (a fake winget that always answers `0x8A15000F`: it updates the sources, tries once more and stops, before anything that changes the machine); its success path goes on to those installs and is checked only in the test VM, and hasn't been (`docs/optional-goals.md`). That test is skipped in an elevated shell, as the script refuses one. `bootstrap.cmd`'s test runs it from a copy of the repo without `mise.toml`, so the checks stop it the same way. Each `.cmd` in the repo root is checked for CRLF line endings and a `.gitattributes` entry, since cmd.exe misreads LF. Trade-off: a fake `dsc` call starts `cmd` and pwsh, about 2s a test with `Invoke-Dsc.ps1`'s own `Get-AppxPackage`, for tests that run the scripts' real path to dsc.

`demos/` holds things run by hand to watch how something behaves, with nothing to pass or fail, kept apart from the tests in `tests/`. Their recipes are in `demos/justfile`, not the main one: run `just <recipe>` from `demos/`, or `just -f demos/justfile <recipe>` from the root. `demos/dsc-messages/` (`just dsc-messages <doc> [dsc args]`) is a visual check of how DSC shows lines a resource writes to stderr (levels, live output, Include nesting). Its README records the results per DSC version. Its stand-in resource `Test/SlowList` is outside `dsc/resources`, so `just dsc` never discovers it.

`surveys/` holds things we run to gather information: how winget, DSC, installers or Windows really behave, measured to settle a question rather than assumed. See `surveys/README.md`. They're kept out of `tests/`, which `just test` runs on every change against fakes, because a survey runs against the real tools, usually attended in the test VM, and only when there's a question to answer. A survey may use Pester, run through `Invoke-Tests.ps1` from `surveys/justfile`, and may assert the behaviour it has recorded so that a rerun flags a change. Each survey's README records how to run it and what it found, with dates and versions. `surveys/winget-paths/` compares how `winget install`, `Microsoft.WinGet/Package` and `Install-WinGetPackage` install the same packages.

A test VM's computer name doesn't decide its configuration, so pass the host: `.\install.cmd vm`.
For a quick run, use the `vm-quick` host (`.\install.cmd vm-quick`). It goes through every step of `just install` (features, WSL, both configurations, `check`, `post-install`) and every kind of resource, with the shared modules that configure rather than install included as they are. The package documents are replaced by a few small packages in `dsc/hosts/vm-quick/`, chosen so each package resource and the Scoop list still take their paths: a `Microsoft.WinGet/Package` already installed (Edge) and one to install machine-wide (WinDirStat), a `Winfiles.WinGet/Package` with `_scope: User` (gh, which without a scope gets its machine-wide MSI and a UAC prompt), and a bare Scoop name and a `bucket/name`. emily's WSL document on it, `dsc/users/emily@vm-quick/wsl.dsc.yaml`, installs a pinned Alpine minirootfs in place of NixOS-WSL, and leaves out `~/.wslconfig` and `~/.wslgconfig`, which are emily's on iris only (`wsl --install --from-file` takes its `.tar.gz`: installed through `Winfiles/WslDistribution` with its sha256 on iris, 2026-11-15). Every Scoop bucket is still added. Its `# post-install:` note is the reminder of what it leaves out. Trade-off: a package that only fails in the real lists, or a NixOS-WSL image problem, only shows up under `vm`, so run `vm` before relying on a change to either. Revisit if the two drift, for example when a shared module gains an install that `vm-quick` doesn't cover. Test a clean install in that VM, not in Windows Sandbox: the Sandbox doesn't expose virtualization to its guest, so WSL2 can't run there, and it has no Store or winget. The script creates the VM and doesn't start it. It fixes the screen at 1920×1080 for basic `vmconnect` sessions (the VM's own console); an enhanced session (Remote Desktop over VMBus, with a shared clipboard) sizes it to the window. It prints the `Checkpoint-VM` and `Restore-VMCheckpoint` commands for taking a `clean` checkpoint after Windows setup and returning to it. Without `-Unattended` the VM boots the ISO into Windows Setup. With it, Setup is skipped: the script applies `Windows 11 Pro` from the ISO to the VHDX, runs `bcdboot`, and writes `Windows\Panther\unattend.xml`, which answers OOBE, creates a local administrator named after you, and signs it in automatically at every boot, so the install's restart needs no attention. The administrator's password is blank, and the specialize pass sets `LimitBlankPasswordUse` to 0, which by default limits blank passwords to the console. So a basic session opens on the desktop, an enhanced session signs in with one click on **Sign in**, and PowerShell Direct needs no password; a restart comes back by itself in either session (checked 2026-10-29 on 26300). The VM's notes record the administrator (`Local administrator: <user> / `, with nothing after the slash), and `scripts/testvm.ps1` reads them for the PowerShell Direct scripts. Trade-off: a blank-password administrator that accepts remote sign-ins, acceptable only because the VM is a throwaway behind the Default Switch's NAT; never do this on a real machine. It replaced a generated password kept in the notes, which every sign-in through an enhanced session made you type. The VM has no sleep states (`powercfg /a`), so it never asks to sign in on wake. The computer name defaults to the VM name, and Setup rejects one longer than 15 characters at first boot, so the script checks it up front; pass `-ComputerName` for a longer `-Name`. The VM stays unactivated, which doesn't affect winfiles.

`just test-vm-copy` packs the repo with `git archive` (by default the working tree: commits plus uncommitted changes to tracked files, through `git stash create`; untracked files are left out) and copies it in over PowerShell Direct, signing in with the administrator from the VM's notes (`-Credential` for a VM installed by hand). It replaces `~\src\winfiles` in the VM, so edits made inside the VM are lost.
PowerShell Direct sessions run elevated with no UAC, so run `bootstrap.cmd` and `install.cmd` in the VM's desktop, and keep `test-vm-shell`, `test-vm-run` and `test-vm-log` for reading results, such as `just test-vm-run <name> 'mise exec -- just check vm'`. Under them, Scoop's installer would refuse to run and the gsudo prompt would never show. `just test-vm-unelevated <name> '<command>'` (`Enter-TestVm.ps1 -Unelevated`) starts a command from here without elevation, through a scheduled task in the VM for its user (Interactive, Limited, Windows PowerShell 5.1), reading the output back as it runs: `just test-vm-copy` then `just test-vm-unelevated winfiles-test 'cmd /c .\bootstrap.cmd'` and `'cmd /c .\install.cmd vm-quick'` ran a clean `vm-quick` install (checked 2026-11-18, from `updated`; `docs/reference/test-vm.md`). It saves typing and returns the output, but it isn't unattended: UAC prompts still show on the VM's desktop and wait for a click, and after the restart someone signs in and presses Enter in the resume window (the command exits 3010 when the VM stops answering or the restart stops the task; the first full run, 2026-11-18, came back as exit 4, the task's 0x40010004 cut by `just`, which is now mapped to 3010). Trade-off: it runs the task in the signed-in session, so it needs someone signed in at the VM (a disconnected session counts). Revisit if a run has to work with nobody signed in.
`just test-vm-log` follows `~\.local\state\winfiles\run.log` in the VM (`scripts/winlog.ps1`'s `[phase]` lines: when the bootstrap and install start and finish, which configuration is running, and the resume after a restart), polling every 2s, and shows its last `-Tail` lines first however old it is, since one file serves every run. `just test-vm-log -All` also follows winget's `DiagOutputDir`, which is what a run writes while a package installs, for the detail behind a failure. Each package adds files there, and the COM log and an installer's log are active at once, so with `-All` it follows every `*.log` written to since a minute before it started, with a header when the output moves to another file. (`-All`, not `-Debug`: that is a PowerShell common parameter, which a `[CmdletBinding()]` script reserves.) The bootstrap's lines are written by Windows PowerShell 5.1 (ANSI) and the install's by pwsh (UTF-8 without a mark), and the watch reads `run.log` as UTF-8, which is only right while the lines stay ASCII. Not yet checked in a real run (as of 2026-11-16): that `run.log` is where the signed-in administrator's `~` points, in the VM. Trade-off: the default hides winget's detail, which a failed package needs; revisit if `-All` ends up being passed every time. It prints `-- following <folder>` once the folder exists (`-- waiting for ... to exist` before), and `-- no new lines for about Ns` every 30s (`-Heartbeat`, in polls) with nothing printed, so quiet can be told from stuck. It keeps a byte offset per file, so a large MSI log isn't reread, but it opens each followed file on every poll, because a directory listing can lag behind a writer that keeps its handle open. The encoding comes from each file's byte order mark (UTF-16 either way, or UTF-8 with or without one), and a file that existed before the start shows its last `-Tail` lines, read from its last 64KB only. Its watch scriptblock runs under Windows PowerShell 5.1 in the VM, so it has to stay compatible, and PowerShell Direct sends only the scriptblock, so the functions it uses are defined inside it rather than at the script's top level. The scriptblock takes the folder as `-Directory` and a number of polls as `-Polls` (0, the default, follows until the session ends), so `tests/scripts/Watch-TestVmLog.Tests.ps1` runs it without a VM: it takes `$watch` from the script's AST, runs it under `powershell.exe` against scratch logs, and covers the four encodings, the 64KB tail of a large UTF-16 file, a line split across two writes and the header at each move between files (a mutation that stopped skipping the cut line failed the large-file test, 2026-11-16). The default folder has a wildcard in the middle of its path, which makes `Get-ChildItem` list the matching folder itself rather than its files, so the script resolves the path first; a test with a wildcard path covers that (it was missed while every test passed a literal folder, and the watch showed nothing in a real run, 2026-11-16). The two tests that write between polls start the process and wait about 2s for the second poll. The host side, `Get-VM` and the reconnect, needs a running VM. A VM that isn't running fails with a message; once following, a guest restart reconnects and a stopped VM ends it. The host's own messages are set apart from the log lines, which come from the VM: a lost connection is a yellow warning, and once the first line of the new session arrives (the watch always prints a status line on its first poll) a green `Reconnected to '<name>', following again.` with a blank line before it; a stopped VM is a warning too. The reconnect was seen working by the user on 2026-11-16 (its first version was a plain `-- reconnected` line that didn't stand out); the colours are not yet checked in a real run, and neither is a paused VM. A paused VM isn't `Running`, so if `Invoke-Command` throws the loop warns "VM '...' stopped (state: Paused)." and exits, and if it hangs nothing prints, not even the heartbeat, which runs in the guest. Restart `just test-vm-log` after resuming a VM. `Winfiles/Wsl` writes `[wsl]` lines there (the arguments it runs `wsl.exe` with, each line of its output, and its exit code), because DSC shows a resource's stderr at trace level only; the output lines are read once `wsl.exe` has exited, so they carry its finish time and a quiet gap before them is the download or install (seen 2026-11-18, `wsl --update` from 2.3.26 to 3.0.5, about 40s). Trade-offs: Scoop and DSC don't write there, so those parts of a run look idle; a line with no line ending yet stays hidden until it gets one; and it asks for UAC, because `Get-VM` is denied otherwise (checked on iris, where the user isn't in Hyper-V Administrators). It's outside the run, so a run needs no change to be followed. Revisit if the Scoop or DSC gap gets in the way, which a stable log written by `Write-ResourceMessage` could fill, or if the UAC prompt becomes a nuisance.
