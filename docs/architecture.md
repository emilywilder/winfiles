# Architecture

How the configuration is structured, and the reasons behind each area.

The state is described with DSC v3, and the root `justfile` drives it. The earlier just modules, exported winget/Scoop package lists and monolithic `modules.dsc.yml` were removed; git history has them.

- **Structure, modelled on NixOS and Home Manager (see nix-starter-configs):** each configuration is an entry document directly in `dsc/`, split by the privileges `set` needs. `<host>.system.dsc.yaml` is like `nixosConfigurations.<host>`: it needs an elevated shell, and `just system` applies it. `<user>@<host>.home.dsc.yaml` is like a standalone `homeConfigurations."<user>@<host>"`: it runs unelevated, and `just home` applies it. Entries only list Includes. Reusable documents go in `dsc/modules/system` and `dsc/modules/home`, and one machine's differences go in `dsc/hosts/<host>/`. `just install` applies system then home, so ordering between them lives in the justfile, while `dependsOn` orders Includes inside an entry. A `dependsOn` can't cross from one to the other. The hosts are `iris`, `vm`, for test VMs, which has every shared module and none of a real machine's hardware, and `vm-quick`, a quicker test host (see `docs/testing.md`). To add a host, create `dsc/hosts/<host>/` and copy a pair of entries, then edit their module lists.
  `configurationFile` paths resolve relative to the folder of the top-level document (the one passed to `--file`), so a configuration works from any working directory. In DSC 3.3.0 (and 3.2.3) this also applies to nested Includes. DSC 3.3.0 also refuses `..` in these paths, so entries have to stay directly in `dsc/`, above what they include. Modules don't include each other, so each one also runs on its own, and entries state the ordering.
  Trade-off: each entry repeats its module list, where Nix would import a common file. A shared layer of Includes works, but two levels of Include lose every resource message below `trace` (`demos/dsc-messages/README.md`). Revisit once there's a third real host or that DSC bug is fixed.
  Modules hold nothing specific to one person or machine, so the project can become a starting point for others later: per-machine differences go in `dsc/hosts/` or an entry. A document that needs elevation for any of its resources goes in `modules/system`. `dsc/templates/` is reference material and is deliberately left out of the configurations.
- **Optional features:** `dsc/hosts/<host>/features.dsc.yaml` holds the Windows optional features a host relies on (Virtual Machine Platform, plus Hyper-V on iris, which hosts the test VMs), in one `Microsoft.Windows/OptionalFeatureList`. Add new features there. DISM doesn't enable a feature's children along with it, so each one is listed, parents first. The resource needs elevation even for `get`, and DSC then refuses the whole run, so the document is left out of the entries, which keeps their `test` unelevated. `just system` sets it on its own, first among the elevated steps. Check it with `just dsc config test --file dsc/hosts/iris/features.dsc.yaml` from an elevated shell. Trade-off: `just check` doesn't cover features. A custom resource reading `Win32_OptionalFeature` over CIM (unelevated, as `wsldistribution.ps1` does) would bring them back in, at the cost of a script to maintain; revisit if features drift unnoticed.
- **Packages:** each feature (base, dev, gaming, internet, productivity, media) has a document with the same name in `dsc/modules/system` and `dsc/modules/home`. Each winget package is a resource of its own: a `Microsoft.WinGet/Package` in `modules/system` and the hosts' system documents, and a `Winfiles.WinGet/Package` with `_scope: User` in `modules/home` and the hosts' home documents (`name` is the id, `source: winget`, `acceptAgreements: true`), with comments between them grouping the packages by purpose. Each `modules/home` document also holds at most one `Winfiles/ScoopPackageList`. `modules/system/runtimes.dsc.yaml` holds the shared runtimes, and `dsc/hosts/<host>/hardware.dsc.yaml` and `home.dsc.yaml` hold what only one machine wants. MSIX frameworks (VCLibs, UI.Xaml, .NET Native, Windows App Runtime) are left out, since the image and the Store supply most of them, and winget installs one an app declares along with it: `winget install`, with and without `--scope user`, and `Microsoft.WinGet/Package` installed ChromaControl and the UI.Xaml 2.6 it declares, unelevated and elevated (`surveys/winget-paths`, 2026-11-17). `Install-WinGetPackage` didn't (`0x8A150110`, a fault in the COM API it uses), so while the lists installed through it, UI.Xaml 2.6 was listed just before ChromaControl. Revisit if a new app's dependency fails to install: list the dependency first. Removing a package's resource doesn't uninstall it; set `_exist: false` and apply it first. A failed package exits non-zero and stops that configuration's `set` (`docs/install.md`). Trade-off: each package is a `winget dscv3` process that looks up its own package, about 0.79s each for `Microsoft.WinGet/Package` (median of 49 on iris) and 1.34s for `Winfiles.WinGet/Package` (median of 40, a pwsh start on top), where a list checked all its packages with one listing for about 1.75s. On iris (2026-11-17) `config test` of the system document went from 46–47s to 73s and of the home document from 34s to 76s, so `just check` from about 85s to about 150s (in the test VM's clean `vm` install, the same day, its two documents took 35s and 37s), for no custom list code, per-package options, uninstalls through `_exist`, and drift that names the package. Revisit if `check` gets slow enough to discourage running it, or if winget gains a batch `test`. To add a package, copy a neighbour under the right comment. It goes in `modules/home` if it has a per-user installer (`winget show --id <id> --exact --scope user` names one) that really runs unelevated, otherwise in `modules/system`. `_scope: User` makes winget pick a per-user installer; a package with no such installer fails instead. Without it, winget picked gh's machine-wide MSI, a UAC prompt in an unelevated run (`surveys/winget-paths`, 2026-11-17). The manifest doesn't prove the installer needs no elevation: KDE Connect's `Scope: user` installer, run with `/S /CurrentUser`, still raises a UAC prompt and waits for it, so it's in `modules/system`. Only a run in the test VM shows this. Scope only applies when installing, and a package already installed counts whichever way it was installed. The system packages set no scope, so winget picks, and it doesn't always pick machine-wide: of iris's system ids, three are installed per-user (`winget list --scope user`, 2026-11-17), KDE Connect and the PowerShell MSIX as above, and `Microsoft.DirectX`, whose user installer winget chose in an elevated run. It still installs unattended, so it stays in `modules/system/gaming.dsc.yaml`. Packages that are managed elsewhere are left out: PowerShell (`modules/system/powershell.dsc.yaml`), DSC itself (`mise.toml`), WSL (`Winfiles/Wsl`, in `modules/system/wsl-platform.dsc.yaml`), IntelliJ IDEA (JetBrains Toolbox), Python and Meld (Scoop, in `modules/home/dev.dsc.yaml`), Discord (Scoop, in `modules/home/internet.dsc.yaml`: winget's installer starts Discord, which asks for UAC mid-run), and whatever is installed by hand (see below). `modules/system/settings.dsc.yaml` also marks the `msstore` source explicit (`Microsoft.WinGet/Source`), so winget only uses it when a command passes `--source msstore`. The bootstrap still passes `--source winget`, since it runs before DSC.
- **Installed by hand:** `dsc/hosts/<host>/manual.yaml` lists what a host needs that can't be installed unattended, each with why. So far that's iCUE, Battle.net and LyX on iris. The TeX engine is Tectonic, from Scoop in `modules/home/productivity.dsc.yaml`. It has no `latex.exe`, which LyX's installer looks for, but LyX can be made to work with it (tested on iris with TeX Live moved out of the way, 2026-11-03). Trade-off: a small engine that winfiles can install unattended, rather than a full distribution it can't. Revisit if something needs a full LaTeX distribution. `just manual [host]` (`scripts/Get-ManualInstaller.ps1`) finds what's missing from the display names in the Uninstall registry keys, downloads it to `~/.cache/winfiles/manual` with `winget download`, which checks the manifest's hash, and never runs an installer. It's outside DSC, so `just check` still means what winfiles can apply by itself, and a host with no list has nothing to do, like `vm`. An entry can move to an ordinary list if its installer turns out to work unattended. PowerShell has no YAML parser, so the list is read with `yq` from `mise.toml`. Trade-off: one more tool in every bootstrap, for a list in the same format as everything else in `dsc/`. Revisit if `yq` is ever the only reason something breaks. The list goes with the host rather than the module because what a machine wants installed by hand differs, but LyX and Battle.net would otherwise belong to shared modules, so a new host has to copy those entries.
- **Scoop:** `Winfiles/ScoopPackageList` is a list: one resource per document, checked with one read of the Scoop root. Entries are `name` or `bucket/name`. `dsc/modules/home/scoop-core.dsc.yaml` declares every bucket (name → repository URL) in one list with no apps, so other modules only list apps and depend on it in the entry. State comes from reading `apps/<name>/current/scoop-install.json` (`install.json` from older Scoop versions) and `buckets/<name>` under the Scoop root, not from running Scoop. `set` adds missing buckets, then makes one `scoop install` call for the missing apps. Scoop's own `Installing '<app>' ...` lines are raised to `WARN`, because that's the lowest level DSC shows by default and a slow download otherwise looks like a hang, and an app or bucket that fails stays in `missing` or `missingBuckets` with the list still exiting 0. `Core` installs git with no buckets, and `Buckets` depends on it, because adding any bucket other than `main` needs git. Scoop finds git through its shims, so before calling Scoop the list puts `<root>\shims` on `PATH` for its own process: the `dsc` process of a fresh `just install` started before Scoop's installer added them to the user `PATH`. Scoop itself is installed by a separate resource, `Winfiles/Scoop`, the first in that document. `Core` depends on it, and the other modules follow through the entry. Its `set` downloads and runs Scoop's own installer, and its only job is installing Scoop; buckets and apps stay with `Winfiles/ScoopPackageList`. The installer refuses an elevated shell, so the resource's `set` exits with 3 there instead of trying. That's why Scoop is in a home configuration. If Scoop is still missing when a list's `set` runs, that list exits with 3 too. Both resources look up the Scoop root with `Get-ScoopRoot` from `dsc/resources/scooproot.ps1` (`$env:SCOOP`, then `root_path` in Scoop's config, then `~\scoop`), which their scripts dot-source.
  Some manifests carry `notes`, which Scoop prints once after installing and which a DSC run hides. `just scoop-notes` (`scripts/Show-ScoopNotes.ps1`) prints them again for every installed app, read from `apps/<name>/current/scoop-manifest.json` (`manifest.json` from older Scoop versions) with `$dir`, `$original_dir` and `$persist_dir` filled in as `scoop info --verbose` does; it runs and changes nothing. It covers every installed app, not just the lists, because a note is about what's on the machine. Notes are free text, and most are optional (context menus, file associations, a profile hook), so they're for review rather than run, and one worth having becomes a resource of its own. It stays out of `just install` and separate from `just post-install`, whose notes are the curated must-dos of one host, so those aren't buried. Trade-off: nothing says when a new note appears, so it only helps when run; revisit if a note that mattered gets missed.
- **WSL:** `dsc/modules/home/wsl.dsc.yaml` writes `~/.wslconfig` and `~/.wslgconfig` from inline content (`Winfiles/FileContentList`, since there's no built-in file resource; the content starts with a `Managed by winfiles` comment because DSC parses a string starting with `[` as an expression). It also installs NixOS-WSL with `Winfiles/WslDistribution` and makes it the default. It does only the Windows side: everything inside the distro (`wsl.*` options, `/etc/wsl.conf`, users) belongs to the NixOS configuration. The resource reads state from the `HKCU\...\Lxss` registration, never unregisters or moves a distribution, and `location` only applies at install time. WSL itself and Virtual Machine Platform come from `Winfiles/Wsl` (below), which `just system` applies before this document. Before installing a distribution, the resource checks through CIM that the feature is enabled, that a hypervisor is running (`Win32_ComputerSystem.HypervisorPresent`), that WSL is 2.4.4 or later, and that no restart is pending, and exits with 3 if not. `Winfiles/Wsl` makes the same checks, so keep the two in step. The hypervisor check catches virtualization turned off in the firmware, or not passed through to a VM, where the feature still reads as enabled and WSL as installed; it runs once no restart is pending, since the hypervisor only starts at boot. Checked 2026-11-18 in the `vm-quick` run (clean, from `updated`): `OOBEComplete` was absent before `home`, and the `WSL First Run` entry and the distribution were both in the desired state in the final `check`. Whether the "Welcome to WSL" window stayed shut wasn't recorded, since only the VM's desktop shows it. `wsl --update` hasn't been through a VM run: the VM's WSL came from `wsl --install`, so nothing was out of date. Before installing NixOS, the document sets `OOBEComplete` under `HKCU\...\Lxss`, which stops the "Welcome to WSL" window opening (from WindowsDeveloperConfig).
- **WSL package and Virtual Machine Platform:** `Winfiles/Wsl` (`dsc/resources/wsl.*`) is `scripts/Install-Wsl.ps1` as a resource. `test` is in the desired state once WSL is installed at `minimumVersion` (2.4.4 by default, the first with `--from-file` and `--name`), Virtual Machine Platform is enabled, no restart is pending and a hypervisor runs. `set` runs `wsl --update` for an old WSL and `wsl --install --no-distribution` for a missing one or a disabled feature, and needs elevation only when there is something to do. It never restarts Windows: it reports `_restartRequired` to DSC (see `Winfiles/ComputerName`) and exits 0, since DSC stops the whole configuration on a non-zero exit. `get` reports it while a restart is pending, and `test` also while Virtual Machine Platform is off, since enabling it leaves one pending, so a `test` run knows ahead of time that `set` will need one. just system applies it first, from `dsc/<host>.restart.dsc.yaml` with the host's features and its name, and it's in the system configurations too, where it's a no-op once WSL is ready, so `just check` tests it. It replaced `scripts/Install-Wsl.ps1`. A WSL older than 2.4.4 gets `wsl --update` first, since whether `wsl --install` updates an installed package hasn't been checked (to do in the test VM: install `wsl.2.3.26.0.x64.msi` from the `updated` checkpoint, then `just system`); neither has the hypervisor check. `wsl.exe` exiting with 1641 (success, restart already started) is accepted like 3010. A WSL that only needs installing or updating isn't predicted to need one, and a restart that Windows Update or an installer asked for is shown by the machine (`scripts/restart.ps1`). The hypervisor is only judged once no restart is pending, since it starts at boot. Checked 2026-11-18 on iris with `dsc config test` and `set` (WSL 3.0.5 ready: in the desired state, a no-op `set`, no restart reported); installing is only tested against mocks, and not yet in the test VM. The built-in `Microsoft.Windows/OptionalFeatureList` has no `test` of its own, so DSC derives it from `get`, which can't report a restart; its schema says it returns `_restartRequired` from `set` when DISM reports a reboot is needed (read from its schema 2026-11-18; not seen, since that needs a feature to be enabled). Checked 2026-11-18 on iris, elevated, with `dsc config test` on `features.dsc.yaml`: nothing reaches `restartRequired`, at the top or on the resource, but each feature's state in `actualState` has DISM's own `restartRequired` field, `"Possible"` for all eight, so DISM says ahead of time whether enabling a feature may need a restart. Not checked: what that field says for a feature that isn't installed (everything is on iris), whether `"Possible"` ever becomes anything but a maybe, and what `set` returns; those need the test VM. Checked in the same run: `Winfiles/Wsl` `test` and `set` elevated, both a no-op (WSL 3.0.5 ready), and `whoami.exe /groups` shows the High mandatory level SID elevated and not unelevated.
  `dsc/modules/system/wsl.dsc.yaml`, in the system configuration because setting it needs elevation, limits inbound access to WSL to SSH into NixOS from the local network. With mirrored networking, inbound traffic to WSL goes through the Hyper-V firewall, per VM creator (WSL's is `{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}`), with host rules that have no program merged in. WSL doesn't register its creator when it's installed or when its service starts (checked on WSL 3.0.3, in a test VM without Hyper-V), so on a new install the document creates the setting itself. The document sets WSL's default inbound action to Block, on the creator and each of its profiles, and declares one Hyper-V rule: TCP 2122 (NixOS's sshd port, set in the NixOS configuration), Private profile, `LocalSubnet`. Another service in NixOS that should be reachable from the network needs its own rule there. `Microsoft.Windows/FirewallRuleList` only manages host rules, so it's done with the NetSecurity cmdlets; reading them needs no elevation, so `test` stays unelevated.
  The pending restart is read from `Component Based Servicing\RebootPending`: right after `wsl --install`, before any restart, the feature already reads as enabled (CIM `InstallState` 1, `RestartNeeded` false on build 26300). The script exits with 3010 whenever that key is set, including after installing and when WSL is already set up, so `just install` stops before DSC. `mise exec` cuts an exit code to its low byte, so anything running the script under it, `just system` included, reports 194 rather than 3010; any non-zero code stops the run, so this does no harm. Trade-off: the key also covers Windows Update, so `just install` stops for a restart Windows Update is waiting on, even on a set-up machine. Installers such as `Microsoft.DotNet.Framework.DeveloperPack.4.6` refuse to run then anyway ("RebootPending = 0" bundle condition, seen in the test VM 2026-10-29). Revisit if that stops become a nuisance.
  When the script has just installed WSL and the key is set, it runs `Restart-Computer` after a 30-second warning, then still exits with 3010 so DSC doesn't start during the shutdown. With WSL already set up it only warns, because `just system` runs on working machines, where a restart could come from Windows Update and take open work with it. There's no `-Force`, so an app with unsaved work can still stop the restart. So does a locked screen: `Restart-Computer` fails with "The machine is locked and cannot be shut down without the force option", and the script then warns "Restarting failed (...)", says to restart and rerun, and still exits with 3010 (seen in the test VM 2026-11-15, whose screen locked while the run was left unattended). Someone watching the run won't have a locked screen; an unattended test VM can. Trade-off: the restart closes the terminal. `install.cmd` continues through a `RunOnce` entry, once Enter is pressed (`docs/install.md`), but after a plain `just install`, rerunning it is on you, and the warning is the only reminder. Revisit if that gets missed.
  `Winfiles/Wsl` replaced `scripts/Install-Wsl.ps1`, which ran under Windows PowerShell 5.1 so it would work before pwsh was installed, until the bootstrap began running `mise install` first (5.1 turned `wsl.exe`'s "not installed" on stderr into a fatal error). The resource needs pwsh, like the others, so it no longer runs by hand on a bare machine. Revisit if the bootstrap ever has to run before mise.
  The resource runs `wsl.exe` through `cmd /c "wsl.exe ... <con > file 2>&1"`, because the inbox `wsl.exe` in System32, the one a machine without the WSL package has, exits 1 with only "For more information please visit https://aka.ms/wslinstall" when its stdin isn't a console, and under DSC it is DSC's pipe. `<con` makes cmd read the console the process is attached to instead. Checked 2026-11-18 in the test VM, running `wsl --install --no-distribution` elevated from the `updated` checkpoint: from a console it worked; with output piped it worked; with stdin piped it failed, with or without `<NUL`; with stdin piped and `<con` it worked, with cmd returning the exit code and the output in the file. Also tried, and replaced: `start /wait` in a new console, which worked but opened a window and doesn't pass on the exit code (`exit /b 7` came back as 0 on iris). The inbox `wsl.exe` ignores `WSL_UTF8` and writes UTF-16, so the output has its NULs stripped before it goes into the error message. Trade-off: the output reaches the log only when the install fails, not as progress in the console; revisit if watching it matters. Also checked 2026-11-18: a full `install.cmd vm-quick` run in the test VM, through DSC and `gsudo --direct`, succeeded, so the process is attached to a console there.
- **Custom resources:** these live in `dsc/resources/` as `*.dsc.resource.json` manifests plus scripts. `just dsc` makes them discoverable. Each script dot-sources `common.ps1`, which sets the preferences and provides `Read-ResourceInput` and `Write-ResourceMessage`. The scripts have no `[CmdletBinding()]` or `[Parameter()]`, so `$input` can hold the JSON from stdin. DSC logs plain stderr lines at `trace` only, so a failure has to go through `Write-ResourceMessage error`, and each script's `trap` does that for uncaught errors; it has to be in the script, because a trap only covers the scope that declares it, even when dot-sourced. Output from Scoop and `wsl.exe` stays plain, so see it with `-l trace`. Trade-off: a failure names the package but not the tool's own explanation, which keeps a normal run readable; revisit if failures keep needing `trace`.
  `Winfiles.WinGet/Package` is `Microsoft.WinGet/Package` plus a stop-gap `_scope` (`User` or `Machine`), for the home packages, until App Installer's resource has the canonical one (see `docs/upstream-drift.md`). It takes the same properties, and passes everything but `_scope` to `winget dscv3 package`, as App Installer's manifest does, so winget decides the state and messages. `_scope` only changes `set`: a package that isn't installed is first installed with `winget install --exact --scope`, since `winget dscv3` takes no scope, and `winget dscv3 package --set` then finds it installed (the resource adds `_exist` to the changed properties, which winget then reports empty). Checked in the test VM (2026-11-17): gh with `_scope: User` installed per-user from an unelevated shell, where without a scope winget picks its machine-wide MSI, and a second `set` changed nothing. `get` and `test` ignore the scope a package is in, as winget does. A failed install exits 2, which stops the configuration, like a failed `Microsoft.WinGet/Package`. Trade-off: a pwsh start on top of each winget call, about 0.55s per package (medians of 1.34s against 0.79s for `Microsoft.WinGet/Package`, in `config test` of iris's home and system documents, 2026-11-17), so about 22s more on a `check` for the 40 home ids, for installs that don't raise UAC in `just home` (gh picks its machine-wide MSI without a scope, `surveys/winget-paths`, 2026-11-17). Revisit when the official `_scope` ships. The home packages use it.
  `Winfiles/FileContentList` writes whole text files from inline content, keeping a `.bak` of a file it replaces. `specialFolder` is for folders that can be redirected, such as `MyDocuments` (OneDrive on this machine), which `%USERPROFILE%` can't reach.
  `Winfiles/ComputerName` names the computer after its host: `dsc/hosts/<host>/computername.dsc.yaml`, included by each `dsc/<host>.system.dsc.yaml` (it needs elevation), with the host's name as the default. Windows applies a rename at the next restart, so the resource compares the name it will have (`ComputerName`) with the one it has (`ActiveComputerName`), and `test` is in the desired state only once the active one matches. `set` renames only when the pending name differs, so rerunning it while the rename waits changes nothing and just warns that a restart is needed. Every operation also reports it to DSC as `_restartRequired` (`get`: while a rename waits; `test` and `set`: while the active name isn't the wanted one, so a `test` run shows ahead of time that `set` will need a restart); DSC 3.3.0 collects it into the result's `executionInformation.restartRequired`, checked 2026-11-18 with `dsc config test`, and ignores the same data under `_metadata.Microsoft.DSC`. Checked 2026-11-18 on iris with a scratch resource and `dsc config test` (PowerShell/DSC#975 describes `_restartRequired` inside `_metadata`, so the shapes were compared): a top-level `_restartRequired` is collected into the resource's `executionInformation.restartRequired` and also into the document's own top-level `executionInformation.restartRequired` and `metadata.Microsoft.DSC.restartRequired`; the same data under `_metadata` stays in the resource's `metadata` and is collected nowhere; an entry that isn't `system`, `service` or `process` is still kept in `actualState` and only logs `WARN Resource returned property '_restartRequired' which contains invalid value`; and through `Microsoft.DSC/Include` nothing reaches the top level (the entry is under the Include's `result[]`, each nested resource with its own `executionInformation.restartRequired`), which is why `Get-RestartReport` walks the nested results. DSC only reports it and never restarts (a resource can't restart Windows; `just system` restarts when one is pending, `scripts/Set-System.ps1`, see `docs/install.md`). Microsoft.Windows/Registry was ruled out (it skips the TCP/IP hostname and the name validation that `Rename-Computer` does), and DSC 3.3.0 has no computer resource that I found. The test VMs are renamed `vm` and `vm-quick` too, since their names never picked a host. Trade-off: `just check` fails until the restart (changed 2026-11-18: it used to pass on the pending name, which let a run say it finished under the old name), and `just` still picks the old name from `COMPUTERNAME` until then, so `install.cmd <host>` keeps passing the host. Revisit if a check should fail until the restart. Checked 2026-11-17 on iris with `dsc config test` (the name already matched); a rename and its restart are not yet checked in the test VM.

How PowerShell is set up (this is the non-obvious part). `dsc/modules/system/powershell.dsc.yaml` installs PowerShell and keeps remoting off, and `dsc/modules/home/powershell.dsc.yaml` does the rest:

- PowerShell 7 is the MSIX, which winget installs by default, with `useLatest`, so every `set` brings it to the latest stable release, and the Store may update it in between. 7.7.0 and later ship no MSI (Microsoft's install page, and the v7.7.0 release's assets, checked 2026-11-14), so the MSI would have meant staying on the 7.6 LTS line, which Microsoft Update patches but never moves past, until 7.6's support ends on 2028-11-14. The MSIX costs: it's per user, so other accounts and SYSTEM tasks don't get it; no `PowerShellCore` event-log provider (registering one would point at a version-numbered folder, and registration locks the DLL there); no all-users profiles, `Set-ExecutionPolicy -Scope LocalMachine` or other `AllUsers` scopes; it can't be a remoting endpoint; and its folder changes with each version, so nothing should name a path to `pwsh.exe`. winfiles' own runs use mise's pwsh, and the profiles and module junctions are per-user, so none of these touch winfiles. Trade-off: the latest release and automatic updates, for those machine-wide features; revisit if something needs pwsh 7 machine-wide (another account, a SYSTEM task, script block logging). iris ran the MSI from 2026-11-09 to 2026-11-14. winget counts an MSI install as the same package and finds no MSI to upgrade it to, so an MSI left installed keeps `test` true on 7.6; uninstall it by hand.
  The same document keeps WinRM stopped and Manual, which keeps remoting off for Windows PowerShell 5.1 and any pwsh 7. Remoting is judged by the service alone: WSMan listeners and session configurations need elevation to read, and `Microsoft.Windows/FirewallRuleList` finds rules by display name, which the two WinRM rules share. Trade-off: something that starts WinRM on demand makes `test` false and `set` stops it; revisit if something here needs WinRM. `modules/system/settings.dsc.yaml` registers Microsoft Update with Automatic Updates ("Receive updates for other Microsoft products"), which the PowerShell MSI's `ENABLE_MU` used to do; it's machine-wide, for other Microsoft software too.
- PowerShell's CurrentUser install scope always writes to `Documents\PowerShell\{Modules,Scripts}`. The document points `PSModulePath` (in `powershell.config.json`) at `~/.local/share/powershell/Modules` and replaces both Documents folders with junctions to `~/.local/share/powershell/{Modules,Scripts}`, migrating existing contents and keeping clashes in `.bak` folders.
- With the junctions, the `PSModulePath` setting is redundant in effect. It's kept as a trade-off: `Documents` is redirected to OneDrive on this machine, and the setting keeps module loading off the junction inside it, so only installs go through it. The cost is that if the junction goes missing, CurrentUser installs land outside `PSModulePath`. Revisit if `Documents` stops being redirected (checked 2026-10-28).
- PSGallery is trusted with `Microsoft.PowerShell.PSResourceGet/Repository`, from PSResourceGet 1.3.1, which pwsh 7.7.0 bundles (mise's pwsh, pinned in `mise.lock`). 1.3.1 is the first stable release with DSC manifests: 1.3.0 went from rc2 straight to 1.3.1 (PSGallery, 2026-11-10). DSC finds them because `scripts/Invoke-Dsc.ps1` puts the running pwsh's `Modules\Microsoft.PowerShell.PSResourceGet` on `DSC_RESOURCE_PATH`; the discovery extension that would otherwise find them is deleted (`docs/tooling.md`). The instance has no `uri`, though the schema requires one, because `set` passes it to `Set-PSResourceRepository`, which refuses `-Uri` for PSGallery ("The PSGallery repository has a predefined Uri"). With `uri`, `set` on an untrusted PSGallery failed; without it, `test` and `set` both work and DSC 3.3.0 doesn't enforce the requirement. `test` is DSC's synthetic one, and `metadata.description` doesn't upset it, unlike `RegistryList` and `Service`. Checked 2026-11-16 on iris, with PSGallery untrusted for the run and the repository store (`%LOCALAPPDATA%\PSResourceGet\PSResourceRepository.xml`) restored afterwards. Not yet through a clean install in the test VM.
- Modules are installed with `Save-PSResource` into that path, not through `Microsoft.PowerShell.PSResourceGet/PSResourceList`, which 1.3.1 provides and which would now work through the junction. Its `test` is wrong in two ways (checked 2026-11-16 on iris with `dsc resource test`): an entry without `version` never counts as installed ("'' is not a valid version string"), so `check` would always fail and every `set` reinstall; and only a list's first entry is checked (a `break` in `IsInDesiredState`), so an installed module followed by a missing one reports `inDesiredState: true`. Read from the code but not run: with more than one entry, `set` compares each desired module against every installed one and so can install what's already there, and it uses the last entry's scope for all of them. Upstream PR PowerShell/PSResourceGet#2048 fixes the first two; it was open with changes requested on 2026-11-16. A workaround would be one list per module, each with a range such as `version: '[[0.0,)'` (the doubled `[` stops DSC parsing it as an expression). Trade-off: keep a `PowerShellScript` for 5 modules rather than depend on workarounds for upstream bugs; revisit when a PSResourceGet with #2048 ships in a pwsh that `mise.lock` pins. On switching, modules saved by `Save-PSResource` have no `PSGetModuleInfo.xml`, so `PSResourceList` sees them as missing and reinstalls each once. `Save-PSResource -Path` doesn't depend on the junction existing.
- `Microsoft.DSC.Transitional/PowerShellScript` is still used where nothing official does the job. The remaining way off `Transitional` for these is `Winfiles/*` resources, which get Pester tests; not decided yet.
- Until 2026-11-17 the system configuration also saved `Microsoft.WinGet.Client` into `%ProgramFiles%\PowerShell\Modules`, for `Winfiles/WinGetPackageList`, which installed the packages through it. - `$PROFILE` can't be relocated, so the default profile files become stubs (they start with `# Managed by winfiles (...)`) that repoint `$PROFILE` and dot-source `~/.config/powershell/`. They're written by `Winfiles/FileContentList`, which ignores line endings and trailing whitespace when comparing, so any other edit to a stub makes `test` report false until the next `set`.
- `Microsoft.PowerShell/Profile` is avoided because its `get` is broken (`JSON: EOF while parsing a value`). It ships with PowerShell, not DSC, and fails under both DSC 3.2.3 and 3.3.0.
