# Bootstrap and install

How a machine goes from a fresh Windows 11 install to its configuration: `bootstrap.cmd`, `install.cmd`, `just install` and what each step does.

On a fresh Windows 11 install, from an unelevated terminal in the repo:

```powershell
.\bootstrap.cmd        # winget, mise and mise.toml's tools; lists the hosts; applies nothing
.\install.cmd <host>   # then, from the same terminal or any other; continues at the sign-in after the restart it asks for, once Enter is pressed
```

The bootstrap and the install are separate. The bootstrap gets the machine to where `just install <host>` can run, and reads nothing from `dsc/`. The install assumes only what the bootstrap guarantees: winget's `jdx.mise` on the user `PATH` (winget's change), the repo trusted, `mise.toml`'s tools installed, and a recent App Installer. It never relies on anything else the machine configuration installs, and knows nothing about the bootstrap: it doesn't check for it or name it. The home configuration also lists `jdx.mise`, and manages the bootstrap's copy from then on; that's the handoff, as nix-darwin manages the Nix its installer put there. `docs/dependencies.md` records what the bootstrap leaves behind and how to remove it.

The two `.cmd` files are the way in, one per stage, and the same to call: unelevated, from cmd or PowerShell, arguments passed on, exit code passed back. What runs behind them can change without changing how they're called. A `.cmd` runs whatever the execution policy, which blocks `.ps1` scripts on a fresh install, so each starts Windows PowerShell 5.1 with `-ExecutionPolicy Bypass`, for that one process; the policy is never changed. `.gitattributes` keeps them CRLF, since cmd.exe misreads batch files with LF line endings. Neither puts anything on the persistent `PATH`: `just` and `pwsh` reach a plain terminal only through the host and user configuration (Scoop's `just`, the PowerShell MSIX), so `just install` works there once a machine is configured, but a bootstrapped one has only `install.cmd` (or `mise exec -- just install <host>`).

- `bootstrap.cmd` runs `scripts\Initialize-Winfiles.ps1 <args>` (below).
- `install.cmd` changes to the repo's folder and runs `scripts\Invoke-Install.ps1 <args>` under Windows PowerShell 5.1, which runs `scripts\Start-Clean.ps1 just install <args>` (see "A run inherits nothing" and "Continuing after a restart" below). That reads `PATH` from the registry to find mise in the terminal that ran the bootstrap, where `PATH` predates mise, then goes through `Invoke-Clean.ps1`, which makes the outer `just` `mise.toml`'s too. It works from any folder.

`scripts/Initialize-Winfiles.ps1` runs under Windows PowerShell 5.1, since nothing else is installed yet. Before changing anything it checks for an unelevated shell, x64 (`mise.lock` only covers windows-x64), Windows 11, `winget`, and `mise.toml` and `mise.lock`, lists every problem and stops. It prints what it will do, then:

```powershell
winget install --id Microsoft.AppInstaller --exact --source winget --accept-package-agreements   # treats 0x8A15002B, already current, as success
Add-AppxPackage -RegisterByFamilyName -MainPackage Microsoft.DesktopAppInstaller_8wekyb3d8bbwe -ForceApplicationShutdown   # only if the update was left staged
powershell -File Initialize-Winfiles.ps1 -MiseOnly           # the rest, in a new process
winget install --id jdx.mise --exact --source winget --accept-package-agreements   # unless mise is installed
$env:Path = <machine Path>;<user Path>                       # this process only, so mise is found without a new terminal
mise trust; mise install                                     # mise.toml provides just, pwsh, gsudo, yq and DSC
mise exec -- just hosts                                      # checks the tools run a recipe; lists the configurations
```

`just hosts` is its check that it worked: it runs mise's `just`, which runs a recipe line in mise's `pwsh`, so a failure there stops the bootstrap with an error instead of leaving it for the install to find. It ends by printing `.\install.cmd <host>`. It takes no host: running the install is a separate step. Each step skips what's already done.
`--source winget` keeps winget away from the `msstore` source, which on a fresh install stops to ask you to accept its terms (and sends your region).
`--accept-package-agreements` accepts mise's licence without a prompt. winget still asks for UAC to install the Visual C++ runtime that `jdx.mise` depends on; the script says so first.
App Installer comes first because a new Windows image can ship one too old for the install, which relies on winget and its DSC module. With 1.26.509 (winget 1.11, seen in the test VM 2026-11-02, on an image that hadn't been through Windows Update) the WinGet module fails when elevated (`Failed to create instance: 0x800706BA`), though not unelevated, and `Microsoft.WinGet/Source` removes `msstore`, then fails to add it back. Upgrading unelevated takes no prompt, and winget 1.29 fixes both. Only the bootstrap does this, so on an old image run the bootstrap before `just install`. The rest runs in a new process because a `winget install` in the same process right after App Installer updated itself failed twice out of twice (`Unrecognized command: '...\WindowsApps\winget.exe'`, 1.29.379 to 1.29.380, test VM 2026-11-15), and in a new process it worked. The update can also stop short of registering: on 2026-11-17 in the test VM, the same update from `updated` reported success, but winget's log had `0x80073D02: Unable to install because the following apps need to be closed Microsoft.DesktopAppInstaller_1.29.379.0`, the app being winget itself. 1.29.379 stayed registered, and Windows registered 1.29.380 at the next sign-in, the one after the WSL restart. That swap moved the old package folder away while the resumed install's system step was starting, and DSC failed with exit code 2 before running winget. So when winget reports success and the registered version (`(Get-AppxPackage Microsoft.DesktopAppInstaller).Version`, the check Microsoft's App Installer page gives) hasn't changed, the bootstrap registers the staged update itself, with `Add-AppxPackage -RegisterByFamilyName -MainPackage Microsoft.DesktopAppInstaller_8wekyb3d8bbwe -ForceApplicationShutdown`, and stops if that doesn't take. Trade-off: this covers only the update the bootstrap starts. The Store can update App Installer at any time, and that could swap it under a running install the same way; revisit if a run fails like this without a bootstrap just before it.
Reloading `PATH` from the registry only changes the script's own process, which the `PATH` constraint allows: winget adds mise's folder to the user `PATH` and makes no link in `WinGet\Links`. Its `Command line alias added: "mise"` line names the package's commands; it isn't a link either (checked in the test VM with winget 1.29.380, 2026-11-16: no `Links` folder, and `...\WinGet\Packages\jdx.mise_...\mise\bin` on the user `PATH`). It can't help in the middle of `just install`: a process started before Scoop was installed never sees its shims.
`mise.toml`'s `min_version` is the mise winfiles was last checked with. Neither the bootstrap, which skips an installed mise, nor the home configuration's list upgrades it, so an older mise stops with `mise version ... is required` and the `winget upgrade jdx.mise` hint (checked on iris 2026-11-15).

`just install [host] [user]` defaults to the computer name and username, and fails before any change when there's no configuration for them. It runs these, in this order. Each one skips what's already done:

```powershell
gsudo --direct mise exec -- pwsh -File ./scripts/Set-System.ps1 <host> # `just system`, through Invoke-AsAdmin.ps1: one UAC prompt, same console (none from an elevated shell)
                                                             #   tests dsc/<host>.restart.dsc.yaml (optional features, WSL, the computer's name) and says which will need a restart
                                                             #   applies it where it differs: scripts/Set-Winfiles.ps1 dsc/<host>.restart.dsc.yaml
                                                             #   the gate: while Windows has a restart pending, restarts it (when this run made it pending) or stops, exit 3010
                                                             #   applies dsc/<host>.system.dsc.yaml (WSL and the computer's name again, as no-ops)
                                                             #   restarts, exit 3010, if only the new name is still pending
mise exec -- pwsh -File ./scripts/Set-Winfiles.ps1 dsc/<user>@<host>.home.dsc.yaml   # `just home`, through Invoke-AsUser.ps1: unelevated (from an elevated shell, `gsudo -i Medium`); installs Scoop itself first
mise exec -- pwsh -File ./scripts/Test-Winfiles.ps1 dsc/<host>.system.dsc.yaml dsc/<user>@<host>.home.dsc.yaml   # `just check`: lists what's missing; exits 1 if anything is
mise exec -- pwsh -File ./scripts/Show-PostInstall.ps1 dsc/hosts/<host>   # `just post-install`: prints what's still to do by hand
```

A step winfiles can't do goes in a YAML comment in `dsc/hosts/<host>/` that starts with `# post-install: ` and runs to the end of that block of comment lines. `just post-install` prints these, so the text lives once, beside the setting it's about. So far that's iris's Remote Desktop, which rejected the Microsoft account's password until the account had signed in with it at the sign-in screen, with "only allow Windows Hello sign-in" off for that sign-in (seen 2026-11-04; it kept working with the setting back on). `just install` runs it last, so a stop for a restart or a failed `just check` hides the notes until the run that gets through. Trade-off: nothing can tell whether a note has been done, so they print on every `just install`, even on a set-up machine; revisit if they start being ignored.

A run inherits nothing from the shell that starts it, so it's the same from any terminal. `install.cmd` (through `scripts/Invoke-Install.ps1` and the launcher below), `just system`, `just home`, `just check`, `just manual`, `just post-install` and `just test` each go through `scripts/Invoke-Clean.ps1`, which starts the command under `mise exec` with `Start-Process -UseNewEnvironment`. Windows builds that environment for the user (`CreateEnvironmentBlock`), from the registry and the logon session, so even a caller's changed `USERNAME` or `USERPROFILE` doesn't reach a run, and no list of per-session variables has to be kept. So `just`, `pwsh`, `gsudo` and DSC are always `mise.toml`'s, even when the run starts from plain `just install`, and only the outer `just` and the shell of that one recipe line come from the caller (from `install.cmd`, those are `mise.toml`'s too). Neither mise nor just can clear an environment, which is why this is a script. Trade-off: a variable set only in the calling shell, such as a proxy, doesn't reach a run; set it persistently if a run needs it. Revisit if mise or just gains a way to do this. `just dsc` isn't part of this: it's for working on the configuration by hand.
`install.cmd` can't start `Invoke-Clean.ps1` itself, because right after the bootstrap the only pwsh is mise's, and the terminal that ran the bootstrap has a `PATH` from before mise was installed. So `Invoke-Install.ps1` runs `scripts/Start-Clean.ps1` under Windows PowerShell 5.1, which reads the machine and user `PATH` from the registry, finds mise, and runs `mise exec -- pwsh Invoke-Clean.ps1 just install ...`. It keeps to 5.1's syntax, and arguments with quotes inside them don't survive 5.1 passing them to pwsh (`install.cmd` passes only a host and user). When `PATH` has no `mise` it says so and exits 1, rather than failing the call and exiting 0. Checked with the launcher run from `cmd` with a `PATH` of only `System32` and `Windows` and a stray variable, 2026-11-16 on iris: `just hosts` ran with mise's `just` and pwsh, the variable didn't arrive, `USERNAME` was right and an exit code of 7 came back. Also checked with a full `bootstrap.cmd` then `install.cmd vm-quick` in the test VM, 2026-11-16: everything worked as expected. Checked again 2026-11-16 in the test VM with `Invoke-Install.ps1` in front of it, from the `updated` checkpoint: `Start-Clean.ps1` found mise in the bootstrap's terminal, and in the resume window after the restart. What was ruled out, so it isn't tried again: `install.cmd` starting `Invoke-Clean.ps1` under 5.1 (`-UseNewEnvironment` on 5.1 gives `USERNAME` of `SYSTEM` and no `USERPROFILE`, and 7.3 is needed for quoting); `install.cmd` calling `pwsh` (right after the bootstrap the only pwsh is mise's, and the terminal's `PATH` predates mise, so there is none to find); and relying on the terminal's `PATH` for mise (same reason, which is why the launcher reads the registry). Trade-off: one more process in front of the run (cmd, 5.1, `mise exec`, pwsh, then the new environment's pwsh), which costs about 0.7s (a trivial command through `Start-Clean.ps1` took a median of 2227ms over 8 runs, against 1571ms through `Invoke-Clean.ps1` alone; 5.1 itself starts in about 380ms; 2026-11-16 on iris, with the load controlled). Revisit if the bootstrap can leave mise's pwsh where a `.cmd` can find it.
Each of the two `mise` calls lists the mise configuration in effect (`mise config ls --json`) and, through `scripts/miseignore.ps1` (tested on its own), adds every file other than the repo's `mise.toml` to `MISE_IGNORED_CONFIG_PATHS`, with a warning naming it: the global `~\.config\mise\config.toml`, a `mise.local.toml` or a `mise.toml` in a parent folder would otherwise add its tools and env to every run (a global config's tools were even installed, checked 2026-11-15). `Start-Clean.ps1` does it for the first `mise exec`, and `Invoke-Clean.ps1` again inside the new environment, which drops the variable. The variable takes a `;`-separated list; `,` doesn't work. When the new environment's `PATH` has no `mise`, `Invoke-Clean.ps1` says so and exits 1. Trade-off: one more `mise` call, about 50ms, per recipe.
The recipe line's shell is `pwsh.exe` from `just`'s `PATH`: mise's under `install.cmd`, the caller's under plain `just` (the Store's on iris), and with none `just` fails with `could not find the shell`, so 5.1 only runs `Invoke-Clean.ps1` if someone calls it by hand. It needs pwsh 7.3: `CreateEnvironmentBlock` arrived in 7.1 (by the source; on 5.1 the same switch gives `USERNAME=SYSTEM` and no `USERPROFILE`), and quotes inside arguments pass correctly from 7.3. An older one gets an error and exit 1 from an explicit check, not `#Requires`: a recipe line carries on past that failure, and `exit $LASTEXITCODE` then reports 0.
The command goes through a second pwsh, `pwsh -ExecutionPolicy Bypass -EncodedCommand`. `-UseNewEnvironment` ignores `-Environment`, so that's what restores `PSExecutionPolicyPreference`, and encoding avoids `Start-Process` joining arguments without quoting them. Bypass matters for the scripts recipes run directly (`Set-System`, `Set-Winfiles`, `Test-Winfiles`, `Get-ManualInstaller`, and what they call). The resource manifests pass it themselves, but mise's pwsh defaults to RemoteSigned, which refuses a file with a mark of the web, as a repo from a downloaded ZIP would have (checked with a marked script, 2026-11-04). Trade-offs: about 0.55s more per recipe line (0.15s before, 0.7s after, 4 runs on iris), and the output skips PowerShell's pipeline, so `$x = & ./scripts/Invoke-Clean.ps1 ...` captures nothing, though no recipe does this. Revisit if `-Environment` starts working alongside `-UseNewEnvironment`, which would remove the second pwsh, or if a recipe needs to capture the output.

A Scoop app that fails to install doesn't stop the run: the list logs an `ERROR`, moves on and exits 0, and so does DSC, so the later lists and resources still apply. `just check` then gives `just install` a failing exit code. A winget package is a resource of its own (`Microsoft.WinGet/Package`, or `Winfiles.WinGet/Package` in the home configurations), and one that fails exits non-zero, so DSC stops that `set` there, with winget's code in its error line, and `Set-Winfiles.ps1` reports the document as failed. That was accepted on 2026-11-17: a list carries on so that one bad id doesn't hide the ids after it in the same resource, which can't happen with one resource per package. Any other failure still stops the run where it happens, before `just check`. Each `set` and `check` also writes DSC's JSON results to `~/.local/state/winfiles/dsc/<time>-<set|test>-<document>.json`, which hold each resource's duration; nothing removes them. They're outside the repo because `just test-vm-copy` replaces the repo, and `just dsc` on its own doesn't write them. Trade-offs: `check` adds about 80s to the end of a run (measured on iris), for one list of what's missing; and `just home` on its own exits 0 after a failed Scoop app, so a script has to run `just check` to notice, though a person sees the `ERROR` line and `Set-Winfiles.ps1`'s list of what was left missing. Revisit if `check` becomes slow enough to skip, or if a failed package gets missed.

What a run says. The scripts that report progress append `[phase] message` lines, with the time, through `Write-WinfilesLog` (`scripts/winlog.ps1`, dot-sourced, 5.1-compatible) to `~/.local/state/winfiles/run.log`, which is read with `just test-vm-log` and prints nothing itself: a script writes to the console with `Write-Host` next to the call, and only for what the person needs, which is failures, warnings, what a `set` left missing and `check`'s results (without the phase). Progress (started, applying, done, the bootstrap's steps, `finished`) is in the file only, so the console never says an install finished. Revisit if someone running `install.cmd` by hand wants that line. It is the one record of a whole install across its restarts (outside the repo, like the DSC results; nothing removes it). The phases: `bootstrap` (its three steps and "done"), `install` (a `started` line, then a `finished` line that only prints when `system`, `home` and `check` all passed, so a stop for a restart or a failed check never says it finished), `restart`, `system` and `home` (from `Set-Winfiles.ps1`, and `system` also from `Set-System.ps1`, which logs what it tests, which resources will need a restart and the restart itself: "applying <document>", "flattened to <its flat copy>", then "done in 3m12s, 41 resources", with a warning and the items still missing when a list left some, or "<document>: dsc failed with exit code N"), `check`, and `resume` (from `Invoke-Install.ps1` and `Resume-Winfiles.ps1`, below: the RunOnce entry registered, or not because the path is too long, then kept for a restart or removed with the exit code; after a restart, resumed after sign-in, a restart still pending, Enter pressed, winget's source not reached, and `install.cmd`'s exit code). `Set-Winfiles.ps1` used to discard DSC's JSON, so a successful `home` ended without a word; now its count and time come from it. What DSC and the resources print in between (winget's and Scoop's own output, DSC's progress bar) is unchanged, so there is still more detail for some steps than others. Checked by tests with the fake dsc (`tests/scripts/Test-Winfiles.Tests.ps1`), and against a real `set` result from a vm-quick install (DSC 3.3.0, 2026-11-16): a list's leftovers are in its `afterState.missing`, as `test` has them in `actualState`, but an Include's `set` result isn't the bare list of its resources' results that `test` gives; that list is its `afterState`. Reading only the `test` shape, that run logged `[home] done ... 5 resources` (its Includes) with three Scoop items missing, so `dsclog.ps1` reads both, and the fake gives a `set` Include that shape. Trade-off: the events come from the scripts around DSC, not from inside it, so a long `home` shows nothing between "applying" and "done" apart from the tools' own lines. Revisit with the resource-level events below.

The flat copy (2026-11-17). `Set-Winfiles.ps1` doesn't give DSC the entry document. `scripts/ConvertTo-FlatConfiguration.ps1` writes a copy with each Include replaced by the resources of the document it includes, to `~/.local/state/winfiles/flat/<document>`, and DSC applies that. Since 2026-11-18 every run does the same (`Get-RunDocument` in `scripts/dsclog.ps1`): `just check` (`Test-Winfiles.ps1`) and `Set-System.ps1`'s test of the restart document test the flat copy too, so `check` tests what `set` applied. `just flat=false <recipe>` gives DSC the documents themselves, Includes and all, for `system`, `home`, `check` and every step of `install` (the scripts' `-NoFlatten`); the run log says which route each document took ("flattened to ..." or "not flattened: dsc runs ... itself"). `install.cmd` has no way to pass it, since `Invoke-Clean.ps1` clears the environment and `install.cmd` only passes on `host user`; run `just flat=false install <host>` instead. Checked 2026-11-18 on iris (background load not controlled): `just check iris emily` passed with all 118 resources either way, in 136s through the flat copies and 153s through the entries. It's YAML, written with `yq`, so it can be read to see exactly what ran, or applied by hand with `just dsc config set --file <it>`; `just flatten <document>` writes it without running anything, to the same place, and prints its path; nothing removes it, and each run rewrites it. Why: the wish was DSC's progress bar per package ("4/15 Set '<name>'"), as `dsc config set --file dsc/modules/system/base.dsc.yaml` shows it. Through Includes the bar counts the entry's top level, so it sat at "4/8 Set 'Packages'" for a whole module, and the `dsc` each Include starts draws no bar of its own (its stderr goes to the parent, not a console). Flat, one dsc runs every resource and the bar names each one. Capturing dsc's stdout, as `dsclog.ps1` does, doesn't hide the bar: DSC 3.3.0 draws it through `tracing-indicatif` on stderr, and only stderr has to be a console (checked 2026-11-17 on iris in a conhost window, sampling the screen buffer while `Test/SlowList` documents ran: the bar showed with stdout on the console, with it captured, and with it captured through an Include, where it named the Include; with stderr redirected it didn't). The bar erases itself when it finishes, so a copied transcript doesn't show it. What the copy keeps: an Include's `dependsOn` becomes `dependsOn` on every resource of the Include it names, for each resource of the dependent one, so DSC still does the ordering and still stops at a failure; the included documents' parameters are merged, with an Include's `parametersContent` as their defaults. Includes inside included documents are flattened too, at any depth (since 2026-11-18): each `configurationFile` resolves from the entry's folder, as DSC 3.3.0 does for nested ones, an Include named in a `dependsOn` is looked up among those of the document the `dependsOn` is written in, and a resource gets the `dependsOn` of every Include around it, so two levels lose nothing, unlike two levels run through DSC, which lose the resources' messages (`docs/architecture.md`). It fails, naming the document, rather than guess, on what it doesn't cover: a document that includes itself, directly or through others (naming the chain, `entry.dsc.yaml -> a.dsc.yaml -> sub/b.dsc.yaml -> a.dsc.yaml`), a `dependsOn` loop in the result (naming the resources; DSC would refuse it too, but without saying which Include it came from), a `parametersContent` value that is an expression (DSC passes those values as they are, and as a default one would be evaluated; none of the documents has one), an Include property other than `configurationFile` and `parametersContent`, a top-level key other than `$schema`, `metadata`, `parameters` and `resources` (so `variables`), a `dependsOn` that isn't `resourceId()`, and a resource or parameter name used twice across the entry's documents. Comments aren't kept. Checked on iris (2026-11-17): every entry document flattens (iris 59 and 57 resources, vm 54 and 53, vm-quick 11 and 14); read back, each resource and parameter equals its source apart from `dependsOn`; and `config test` of the flat iris documents gave the same result for every resource as the entries, in 62s against 75s (system) and 73s against 88s (home), since one dsc no longer starts another per Include. `yq` writes the documents' text intact in a console on code page 437, checked with non-ASCII strings, though the documents are ASCII today. Nothing in a normal run tests the entries through real Includes any more: `just flat=false check` is the way to compare, and its results should match `just check`'s resource for resource (what was checked by hand on 2026-11-17, above). Seen in a vm-quick install from `updated` (2026-11-18, e32adb5): the bar named each resource in `system` and `home`; Scoop's lines lost the `trace_message="..."` wrapping and one of the two PIDs, but kept DSC's UTC timestamp and a PID (`2026-11-18T23:42:39.864459Z  WARN PID 9308: Installing 'git' (2.56.1) [64bit] from 'main' bucket`); the restart document was flattened for its test and its `set`, and the restart report still named its resources (`Winfiles/Wsl 'WSL', Winfiles/ComputerName 'Computer Name'`); each DSC result was a flat list, one entry per resource; and `check` passed with all 27 resources. Times, against the c6f5d9d vm-quick run of 2026-11-17 through Includes (one run each, not a benchmark): `system` 56s against 43s and `home` 1m54s against 1m39s, both led by installs whose time varies (PowerShell's MSIX 36.6s against 21.7s, Scoop's Core list 50s against 30s); `check` 11s against 16s. What it leaves as it was: DSC 3.3.0 refuses `..` in a `configurationFile`, and the flattener resolves one without checking, so an entry that used it would pass `just install` and fail under `just flat=false` or by hand; keep entries directly in `dsc/` (`docs/architecture.md`). A `dependsOn` still can't cross from the system document to the home one, but they're separate runs with different elevation, not Includes. `just test` flattens every entry in `dsc/` (`tests/scripts/ConvertTo-FlatConfiguration.Tests.ps1`), so a name used twice across modules fails there rather than at the start of an install. Trade-offs: `just install` and a by-hand `dsc config set` on an entry take different routes to the same resources, and an error names a resource rather than a line in a module, for a bar that names each package, about 15s less per configuration in `set` and in `check`, and results with no Include nesting; and `check` no longer catches a difference between the copy and the entries by itself. Revisit if the entries need an Include feature the copy doesn't cover, or if DSC lets an Include's `dsc` draw its own bar.

The whole run is elevated once, at its start (`install-elevated` runs `install-steps` through `Invoke-AsAdmin.ps1`, after `require` has checked the configurations exist, so a wrong host name never reaches the prompt), so each run asks for UAC once, and the restart comes while someone is watching. `system` runs as it is, `home` and `check` drop to unelevated through `Invoke-AsUser.ps1`, and from an already elevated shell there is no prompt at all. Nothing after the UAC prompt needs attention. `system` and `home` are `[no-exit-message]`, so a stop for a restart shows only the script's warning, not just's red "recipe failed" lines, and `Set-Winfiles.ps1` prints a failure itself, naming the document, which is what tells the restart document and the system document apart inside the one gsudo call, so just's lines would only repeat it. Enabling a feature leaves `RebootPending` set, so `Set-System.ps1` stops the run then, before any installer. gsudo's credential cache (`gsudo cache on`) isn't used: just runs each recipe line in its own process, and the cache's per-process scope hasn't been checked against that.

## Continuing after a restart

`just install` stops with 3010 while Windows has a restart pending, and `Set-System.ps1` restarts Windows itself when this run made the restart pending. `install.cmd` picks the run up again at the next sign-in, through a per-user `RunOnce` entry, so a clean install doesn't wait for someone to notice the restart and rerun it. Only `install.cmd` does this; a plain `just install` still has to be rerun by hand.

The computer's new name only takes effect at a restart, so `Winfiles/ComputerName` reports not in its desired state until the active name matches, and `check` fails while a rename waits (its `set` still renames only when the pending name differs). A clean install restarts once for everything that needs it. `Set-System.ps1` tests `dsc/<host>.restart.dsc.yaml` first: `Winfiles/ComputerName` and `Winfiles/Wsl` report `_restartRequired` from `test` while their `set` will need a restart, so the script can say which ahead of time (the built-in features resource can't from `test`: nothing its `get` returns reaches DSC's `restartRequired`, checked 2026-11-18 elevated on iris. Its `set` does: in a `vm-quick` run in the test VM on 2026-11-18 it returned `_restartRequired: [{system: <computer name>}]` in its `afterState`, which DSC collected into that resource's `executionInformation.restartRequired`, with `changedProperties` `_restartRequired` and `features`, so a restart the features need is known once they are applied, not before. Its per-feature `restartRequired` field says `Possible` for every feature, installed or not (checked 2026-11-18 elevated on iris: Telnet Client, which DISM reports as `Disabled` and DSC as `Staged`, and Virtual Machine Platform, `Enabled` and `Installed`, both said `Possible`, and `test` gave `inDesiredState: false` with `differingProperties: ["features"]` for the missing one), so it can't tell a feature that needs a restart from one that doesn't, and `Set-System.ps1` doesn't use it: a feature that isn't installed isn't known to need a restart until it has been applied, and the pending restart is read from the machine afterwards; see `docs/architecture.md`). It applies what differs, and if Windows then has a restart pending it restarts there, before any installer, and exits 3010; the rename rides along. What counts as pending is read from the machine by `scripts/restart.ps1`, which `Resume-Winfiles.ps1` shares: component servicing, which blocks the run, and a pending rename, which can wait for a restart that's happening anyway. It restarts by itself (30 seconds for Ctrl+C, no `-Force`) only when no restart was pending before this run applied anything, and otherwise only asks, since it may be Windows Update's. When only the rename is pending after the system document (the features and WSL were already done) it restarts then, so a clean install doesn't finish under the old name (found 2026-11-18 in the test VM). DSC 3.3.0 puts `restartRequired` on each resource's own entry in a result, not on the configuration's or an Include's, so `Get-RestartReport` in `scripts/dsclog.ps1` reads the entries `Get-ResourceResult` flattens (checked 2026-11-18 with a probe document inside an Include; it also works on a document that has been flattened). Trade-off: reasons are derived from the machine rather than counted, since a count is lost across the restart the install resumes after and can't see one that Windows Update or an installer asked for. Revisit if a reason is missed. Trade-off: whether a restart blocks installers is the machine's answer (`RebootPending`), not a table of resource types and not something DSC's `_restartRequired` says (it names a system, service or process). Revisit if a resource needs to say it itself. Trade-off: `PendingFileRenameOperations` is not read, since nearly every installer sets it, often for harmless files. Revisit if an install step fails because of it. Trade-off: the rename is applied with the features and WSL, before the first restart, rather than after the installers, so one restart serves all three; the installers then run after a rename, which hasn't been seen to matter. Revisit if renaming ahead of them causes trouble. Checked 2026-11-18 in the test VM, a clean `install.cmd vm-quick` from `updated` (`run.log`): the test of `vm-quick.restart.dsc.yaml` said `a restart will be needed by: Winfiles/Wsl 'WSL', Winfiles/ComputerName 'Computer Name'`, applying it took 51s, the script restarted once, the install resumed after sign-in, the restart document then tested clean, and the system document (45s), the home document (1m30s) and `check` (27 of 27) passed, with `install.cmd` exiting 0, about six minutes from the bootstrap to the end. Before the restart, `set` left the computer named `WINFILES-TEST` with `pendingName` `VM-QUICK` and `activeName` still `WINFILES-TEST`, and `Winfiles/Wsl` at 3.0.5 with `restartPending`; after it `check` found the name in its desired state. The features test, which can't predict a restart, is the one the message leaves out.

`scripts/Invoke-Install.ps1` (under Windows PowerShell 5.1, like `Start-Clean.ps1`) writes `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce\winfiles` before it runs `Start-Clean.ps1 just install <args>`, because writing it afterwards would race the shutdown. When the run ends it removes the value unless the exit code is 3010, or 194, which is 3010 cut to its low byte by `mise exec`. A run that finished or failed leaves nothing behind. The value is `cmd.exe /c start "winfiles" powershell.exe -NoProfile -ExecutionPolicy Bypass -NoExit -File scripts\Resume-Winfiles.ps1 <args>`:

- The window is whichever terminal Windows defaults to, so nothing depends on `wt.exe`, which the home configuration only installs later. `start` returns at once, so startup isn't held up if Explorer waits for RunOnce commands (not checked).
- `Resume-Winfiles.ps1` says what it's doing, stops before UAC if `RebootPending` is still set, waits for Enter (below), waits up to 60s for `cdn.winget.microsoft.com:443` (winget's source, since Wi-Fi can still be connecting at sign-in), then runs `install.cmd <args>` as a child, so the window stays open on the result. That run registers the entry again if it stops for another restart.
- Windows deletes a RunOnce value before running it, and the name has no `!`, so only a run that stops for a restart writes it back: declining UAC or any failure ends the chain, and a restart that's still pending can't keep prompting.
- A command over RunOnce's 260 characters only gets a warning, and the install goes ahead without the resume.
- Both scripts write `[resume]` lines to `run.log` (above), so `just test-vm-log` shows the whole chain across the restart: `system` stopping for it, the entry kept, then the resume and the next `install` run. When `Set-System.ps1` restarts Windows itself, the shutdown ends `Invoke-Install.ps1` before the run returns, so there's no "kept" line: the `system` line saying it's restarting is followed straight by "resumed after sign-in". The entry is there anyway, since it's written before the run (seen in a vm-quick install, 2026-11-16).

The resume waits for Enter before it starts `install.cmd`, and so before the UAC prompt, because a sign-in doesn't mean someone is at the machine. The test VM signs in by itself at every boot (`New-TestVm.ps1 -Unattended`). On 2026-11-17 the resumed vm-quick run asked for UAC straight away with nobody at the VM's window, Windows cancelled the unanswered prompt, gsudo reported `The operation was canceled by the user.`, and `install.cmd` exited 231, ending the chain. Its log line is "continuing: Enter pressed", so the time between it and "resumed after sign-in" is the wait, not the install.

Trade-off: the resume now needs a key press after every restart, even when the person has just signed in themselves, and a restart put off with Ctrl+C can bring the window back days later. In exchange, the UAC prompt only comes once someone has asked for it. Revisit if the resume has to run unattended.

Considered and not done: skipping the resume's UAC prompt with a scheduled task (reasoned 2026-11-16, nothing built or tried). The prompt comes from gsudo in the resumed `just install`. RunOnce can't avoid it: HKCU and HKLM RunOnce both start with the unelevated token, and only an elevated process can create a "run with highest privileges" task, which then starts elevated with no prompt.

- A logon task that runs the whole resume elevated doesn't work: `just home` would run elevated and Scoop's installer refuses that (`Winfiles/Scoop` exits 3).
- A design that would work: the first run's UAC step also registers an on-demand task (no trigger, highest privileges) that runs only the elevated steps (`Set-System.ps1`). The unelevated RunOnce resume stays, and where `just install` calls gsudo it runs `schtasks /run`, waits, and reads the result, then does `home`, `check` and post-install unelevated. Remove the task when the install finishes or fails, not at the start of its run.
- What it costs: a task can't pipe its output into the resume window as gsudo does (a log file to tail, or a console window of its own); a second path through `just install` for the resume only; and an elevated task that runs repo scripts, so any unelevated process that can edit them gets admin while the task exists. Running a copy from `C:\ProgramData\winfiles`, writable only by administrators, would close that at the price of the copy drifting from the repo.
- Why not: too much machinery for one prompt, which comes after a restart when someone is already at the machine. Revisit if the resume has to run unattended (it waits for Enter, above).

## Running an unelevated step from an elevated shell

Checked 2026-11-18 on the dev machine (Windows 11 10.0.26300, UAC on, signed in at the console), from an elevated pwsh. Probe scripts were run by hand and not kept; nothing in the install uses either route yet. Each child recorded its own token, whether it could write HKLM and HKCU, and (for the task) the exit code it handed back.

| | `runas /trustlevel:0x20000 <command>` | Scheduled task, Interactive logon, run level Limited | `gsudo -i Medium --direct <command>` (mise's gsudo 2.6.1) |
|---|---|---|---|
| Integrity level | High, the same as the elevated parent | Medium, the same as a normal shell | Medium, the same as a normal shell |
| `IsInRole(Administrator)` | false | false | false |
| Administrators SID | deny-only | deny-only | deny-only |
| Enabled privileges | 1 | 1 | 1 |
| Write to HKLM / HKCU | no / yes | no / yes | no / yes |
| User, session, `%USERPROFILE%` | same as the parent | same as the parent | same as the parent |
| Exit code back to the caller | no | yes (`exit 7` read back as `LastTaskResult` 7) | yes (`exit 7` read back as 7) |
| Waiting for the child | no: `runas` returned after about 1.6 s, before the child had finished | yes: poll `Get-ScheduledTask` until `Ready` | yes |
| Output | none | none: a task has no console | on the parent's console: stdin, stdout and stderr not redirected; stdout and stderr also captured by a pipe |
| Cost | about 1.6 s | about 1.6 to 2.6 s, including register and unregister | about 2 s for a trivial pwsh child |

- `runas /trustlevel` gives the elevated token with its power stripped (a Safer level), so a role check or an HKLM write sees a non-admin but the integrity level stays High. Software that checks integrity, or that is affected by UIPI, COM or Explorer boundaries, may behave differently from a normal unelevated run. Not usable as a stand-in for "unelevated" without testing each tool through it.
- The Limited task gets the user's own filtered token from the logon session, which is what an unelevated terminal has. Its cost is the console: a task has none.
- `gsudo -i Medium --direct` (checked 2026-11-18 on iris, from an elevated pwsh, with the winget-installed gsudo and with mise's 2.6.1) gives the same token as a normal unelevated shell by every measure above, and keeps the caller's console, so DSC's progress bar (which needs stderr to be a console) would still draw. It is the better route to try first. Not checked: the token's elevation type against a normal shell's (only the rows above), and whether it works with no one signed in.
- Checked 2026-11-18 in the test VM (`winfiles-test`, `updated` checkpoint, build 26300, winget 1.29.380), over PowerShell Direct, where the session is elevated (High, four enabled privileges, administrator) and non-interactive (session 0): `gsudo -i Medium --direct powershell.exe ...` (gsudo 2.6.1, installed with winget there) gave a child that was not an administrator, at Medium integrity, with one privilege and the Administrators SID deny-only. Inside it Scoop's installer ran (`Scoop was installed successfully!`; it didn't refuse, since the child isn't an administrator), `scoop install git` installed 7zip and git, and `winget install --id GitHub.cli --scope user` exited 0 (`Successfully installed`, `Command line alias added: "gh"`). The Scoop folder's owner was the user (`WINFILES-TEST\emily`), not Administrators. So a non-interactive elevated parent can hand the unelevated steps to a child this way, and the steps `home` needs from an unelevated process worked.
- Not checked: the DSC resources themselves (`Winfiles/Scoop`, `Winfiles.WinGet/Package`, `Winfiles/WslDistribution`) through the hop, only the commands they run; the WSL distribution at all (WSL wasn't installed in the VM, and installing it needs a restart); the owner of the winget package's files (the path I looked at wasn't where it installed); a run from the VM's desktop session rather than session 0; the owner and ACLs of files the child creates in places other than `~\scoop`; capturing stdout and stderr (a task has no console, so output would go to a file such as the run log); running with nobody signed in, or from a remote session (Interactive logon needs the user's session).
- A handoff built on the task would register a uniquely named task, run `pwsh -File <script>` hidden with quoted arguments, poll until `Ready`, read `LastTaskResult`, and unregister it in a `finally`.
