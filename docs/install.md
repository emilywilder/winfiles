# Bootstrap and install

How a machine goes from a fresh Windows 11 install to its configuration: `bootstrap.cmd`, `install.cmd`, `just install` and what each step does.

On a fresh Windows 11 install, from an unelevated terminal in the repo:

```powershell
.\bootstrap.cmd        # winget, mise and mise.toml's tools; lists the hosts; applies nothing
.\install.cmd <host>   # then, from the same terminal or any other; rerun it after the restart it asks for
```

The bootstrap and the install are separate. The bootstrap gets the machine to where `just install <host>` can run, and reads nothing from `dsc/`. The install assumes only what the bootstrap guarantees: winget's `jdx.mise` on the user `PATH` (winget's change), the repo trusted, `mise.toml`'s tools installed, and a recent App Installer. It never relies on anything else the machine configuration installs, and knows nothing about the bootstrap: it doesn't check for it or name it. The home configuration also lists `jdx.mise`, and manages the bootstrap's copy from then on; that's the handoff, as nix-darwin manages the Nix its installer put there. `docs/dependencies.md` records what the bootstrap leaves behind and how to remove it.

The two `.cmd` files are the way in, one per stage, and the same to call: unelevated, from cmd or PowerShell, arguments passed on, exit code passed back. What runs behind them can change without changing how they're called. A `.cmd` runs whatever the execution policy, which blocks `.ps1` scripts on a fresh install, so each starts Windows PowerShell 5.1 with `-ExecutionPolicy Bypass`, for that one process; the policy is never changed. `.gitattributes` keeps them CRLF, since cmd.exe misreads batch files with LF line endings. Neither puts anything on the persistent `PATH`: `just` and `pwsh` reach a plain terminal only through the host and user configuration (Scoop's `just`, the PowerShell MSIX), so `just install` works there once a machine is configured, but a bootstrapped one has only `install.cmd` (or `mise exec -- just install <host>`).

- `bootstrap.cmd` runs `scripts\Initialize-Winfiles.ps1 <args>` (below).
- `install.cmd` changes to the repo's folder and runs `scripts\Start-Clean.ps1 just install <args>` under Windows PowerShell 5.1 (see "A run inherits nothing" below), which reads `PATH` from the registry to find mise in the terminal that ran the bootstrap, where `PATH` predates mise, then goes through `Invoke-Clean.ps1`, which makes the outer `just` `mise.toml's too. It works from any folder.

`scripts/Initialize-Winfiles.ps1` runs under Windows PowerShell 5.1, since nothing else is installed yet. Before changing anything it checks for an unelevated shell, x64 (`mise.lock` only covers windows-x64), Windows 11, `winget`, and `mise.toml` and `mise.lock`, lists every problem and stops. It prints what it will do, then:

```powershell
winget install --id Microsoft.AppInstaller --exact --source winget --accept-package-agreements   # treats 0x8A15002B, already current, as success
powershell -File Initialize-Winfiles.ps1 -MiseOnly           # the rest, in a new process
winget install --id jdx.mise --exact --source winget --accept-package-agreements   # unless mise is installed
$env:Path = <machine Path>;<user Path>                       # this process only, so mise is found without a new terminal
mise trust; mise install                                     # mise.toml provides just, pwsh, gsudo, yq and DSC
mise exec -- just hosts                                      # checks the tools run a recipe; lists the configurations
```

`just hosts` is its check that it worked: it runs mise's `just`, which runs a recipe line in mise's `pwsh`, so a failure there stops the bootstrap with an error instead of leaving it for the install to find. It ends by printing `.\install.cmd <host>`. It takes no host: running the install is a separate step. Each step skips what's already done.
`--source winget` keeps winget away from the `msstore` source, which on a fresh install stops to ask you to accept its terms (and sends your region).
`--accept-package-agreements` accepts mise's licence without a prompt. winget still asks for UAC to install the Visual C++ runtime that `jdx.mise` depends on; the script says so first.
App Installer comes first because a new Windows image can ship one too old for the install, which relies on winget and its DSC module. With 1.26.509 (winget 1.11, seen in the test VM 2026-11-02, on an image that hadn't been through Windows Update) the WinGet module fails when elevated (`Failed to create instance: 0x800706BA`), though not unelevated, and `Microsoft.WinGet/Source` removes `msstore`, then fails to add it back. Upgrading unelevated takes no prompt, and winget 1.29 fixes both. Only the bootstrap does this, so on an old image run the bootstrap before `just install`. The rest runs in a new process because a `winget install` in the same process right after App Installer updated itself failed twice out of twice (`Unrecognized command: '...\WindowsApps\winget.exe'`, 1.29.379 to 1.29.380, test VM 2026-11-15), and in a new process it worked.
Reloading `PATH` from the registry only changes the script's own process, which the `PATH` constraint allows: winget adds mise's folder to the user `PATH` and makes no link in `WinGet\Links`. Its `Command line alias added: "mise"` line names the package's commands; it isn't a link either (checked in the test VM with winget 1.29.380, 2026-11-16: no `Links` folder, and `...\WinGet\Packages\jdx.mise_...\mise\bin` on the user `PATH`). It can't help in the middle of `just install`: a process started before Scoop was installed never sees its shims.
`mise.toml`'s `min_version` is the mise winfiles was last checked with. Neither the bootstrap, which skips an installed mise, nor the home configuration's list upgrades it, so an older mise stops with `mise version ... is required` and the `winget upgrade jdx.mise` hint (checked on iris 2026-11-15).

`just install [host] [user]` defaults to the computer name and username, and fails before any change when there's no configuration for them. It runs these, in this order. Each one skips what's already done:

```powershell
gsudo --direct mise exec -- just dsc-set-features <host> wsl-install dsc-set-system <host> # `just system`: one UAC prompt, same console
                                                             #   dsc-set-features: scripts/Set-Winfiles.ps1 dsc/hosts/<host>/features.dsc.yaml
                                                             #   wsl-install: wsl --install --no-distribution; exits 3010 while a restart is pending
                                                             #   dsc-set-system: scripts/Set-Winfiles.ps1 dsc/<host>.system.dsc.yaml
mise exec -- pwsh -File ./scripts/Set-Winfiles.ps1 dsc/<user>@<host>.home.dsc.yaml   # `just home`: unelevated; installs Scoop itself first
mise exec -- pwsh -File ./scripts/Test-Winfiles.ps1 dsc/<host>.system.dsc.yaml dsc/<user>@<host>.home.dsc.yaml   # `just check`: lists what's missing; exits 1 if anything is
mise exec -- pwsh -File ./scripts/Show-PostInstall.ps1 dsc/hosts/<host>   # `just post-install`: prints what's still to do by hand
```

A step winfiles can't do goes in a YAML comment in `dsc/hosts/<host>/` that starts with `# post-install: ` and runs to the end of that block of comment lines. `just post-install` prints these, so the text lives once, beside the setting it's about. So far that's iris's Remote Desktop, which rejected the Microsoft account's password until the account had signed in with it at the sign-in screen, with "only allow Windows Hello sign-in" off for that sign-in (seen 2026-11-04; it kept working with the setting back on). `just install` runs it last, so a stop for a restart or a failed `just check` hides the notes until the run that gets through. Trade-off: nothing can tell whether a note has been done, so they print on every `just install`, even on a set-up machine; revisit if they start being ignored.

A run inherits nothing from the shell that starts it, so it's the same from any terminal. `install.cmd` (by way of the launcher below), `just system`, `just home`, `just check`, `just manual`, `just post-install` and `just test` each go through `scripts/Invoke-Clean.ps1`, which starts the command under `mise exec` with `Start-Process -UseNewEnvironment`. Windows builds that environment for the user (`CreateEnvironmentBlock`), from the registry and the logon session, so even a caller's changed `USERNAME` or `USERPROFILE` doesn't reach a run, and no list of per-session variables has to be kept. So `just`, `pwsh`, `gsudo` and DSC are always `mise.toml`'s, even when the run starts from plain `just install`, and only the outer `just` and the shell of that one recipe line come from the caller (from `install.cmd`, those are `mise.toml`'s too). Neither mise nor just can clear an environment, which is why this is a script. Trade-off: a variable set only in the calling shell, such as a proxy, doesn't reach a run; set it persistently if a run needs it. Revisit if mise or just gains a way to do this. `just dsc` isn't part of this: it's for working on the configuration by hand.
`install.cmd` can't start `Invoke-Clean.ps1` itself, because right after the bootstrap the only pwsh is mise's, and the terminal that ran the bootstrap has a `PATH` from before mise was installed. So it runs `scripts/Start-Clean.ps1` under Windows PowerShell 5.1, which reads the machine and user `PATH` from the registry, finds mise, and runs `mise exec -- pwsh Invoke-Clean.ps1 just install ...`. It keeps to 5.1's syntax, and arguments with quotes inside them don't survive 5.1 passing them to pwsh (`install.cmd` passes only a host and user). When `PATH` has no `mise` it says so and exits 1, rather than failing the call and exiting 0. Checked with the launcher run from `cmd` with a `PATH` of only `System32` and `Windows` and a stray variable, 2026-11-16 on iris: `just hosts` ran with mise's `just` and pwsh, the variable didn't arrive, `USERNAME` was right and an exit code of 7 came back. Also checked with a full `bootstrap.cmd` then `install.cmd vm-quick` in the test VM, 2026-11-16: everything worked as expected. What was ruled out, so it isn't tried again: `install.cmd` starting `Invoke-Clean.ps1` under 5.1 (`-UseNewEnvironment` on 5.1 gives `USERNAME` of `SYSTEM` and no `USERPROFILE`, and 7.3 is needed for quoting); `install.cmd` calling `pwsh` (right after the bootstrap the only pwsh is mise's, and the terminal's `PATH` predates mise, so there is none to find); and relying on the terminal's `PATH` for mise (same reason, which is why the launcher reads the registry). Trade-off: one more process in front of the run (cmd, 5.1, `mise exec`, pwsh, then the new environment's pwsh), which costs about 0.7s (a trivial command through `Start-Clean.ps1` took a median of 2227ms over 8 runs, against 1571ms through `Invoke-Clean.ps1` alone; 5.1 itself starts in about 380ms; 2026-11-16 on iris, with the load controlled). Revisit if the bootstrap can leave mise's pwsh where a `.cmd` can find it.
Each of the two `mise` calls lists the mise configuration in effect (`mise config ls --json`) and, through `scripts/miseignore.ps1` (tested on its own), adds every file other than the repo's `mise.toml` to `MISE_IGNORED_CONFIG_PATHS`, with a warning naming it: the global `~\.config\mise\config.toml`, a `mise.local.toml` or a `mise.toml` in a parent folder would otherwise add its tools and env to every run (a global config's tools were even installed, checked 2026-11-15). `Start-Clean.ps1` does it for the first `mise exec`, and `Invoke-Clean.ps1` again inside the new environment, which drops the variable. The variable takes a `;`-separated list; `,` doesn't work. When the new environment's `PATH` has no `mise`, `Invoke-Clean.ps1` says so and exits 1. Trade-off: one more `mise` call, about 50ms, per recipe.
The recipe line's shell is `pwsh.exe` from `just`'s `PATH`: mise's under `install.cmd`, the caller's under plain `just` (the Store's on iris), and with none `just` fails with `could not find the shell`, so 5.1 only runs `Invoke-Clean.ps1` if someone calls it by hand. It needs pwsh 7.3: `CreateEnvironmentBlock` arrived in 7.1 (by the source; on 5.1 the same switch gives `USERNAME=SYSTEM` and no `USERPROFILE`), and quotes inside arguments pass correctly from 7.3. An older one gets an error and exit 1 from an explicit check, not `#Requires`: a recipe line carries on past that failure, and `exit $LASTEXITCODE` then reports 0.
The command goes through a second pwsh, `pwsh -ExecutionPolicy Bypass -EncodedCommand`. `-UseNewEnvironment` ignores `-Environment`, so that's what restores `PSExecutionPolicyPreference`, and encoding avoids `Start-Process` joining arguments without quoting them. Bypass matters for the scripts recipes run directly (`Set-Winfiles`, `Test-Winfiles`, `Get-ManualInstaller`, `Install-Wsl`, and what they call). The resource manifests pass it themselves, but mise's pwsh defaults to RemoteSigned, which refuses a file with a mark of the web, as a repo from a downloaded ZIP would have (checked with a marked script, 2026-11-04). Trade-offs: about 0.55s more per recipe line (0.15s before, 0.7s after, 4 runs on iris), and the output skips PowerShell's pipeline, so `$x = & ./scripts/Invoke-Clean.ps1 ...` captures nothing, though no recipe does this. Revisit if `-Environment` starts working alongside `-UseNewEnvironment`, which would remove the second pwsh, or if a recipe needs to capture the output.

A package that fails to install doesn't stop the run: the list logs an `ERROR`, moves on and exits 0, and so does DSC, so the later lists and resources still apply. `just check` then gives `just install` a failing exit code. Any other failure still stops the run where it happens, before `just check`. Each `set` and `check` also writes DSC's JSON results to `~/.local/state/winfiles/dsc/<time>-<set|test>-<document>.json`, which hold each resource's duration; nothing removes them. They're outside the repo because `just test-vm-copy` replaces the repo, and `just dsc` on its own doesn't write them. Trade-offs: `check` adds about 80s to the end of a run (measured on iris), for one list of what's missing; and `just system` and `just home` on their own exit 0 after a failed package, showing only the `ERROR` line, so run `just check` after them. Revisit if `check` becomes slow enough to skip, or if a failed package gets missed.

The elevated steps come first and share one gsudo call, so each run asks for UAC once, at the start, and the restart comes while someone is watching. Run on its own, `just wsl-install` elevates itself in a separate window instead. Nothing after the UAC prompt needs attention. `wsl-install` and `system` are `[no-exit-message]`, so a stop for a restart shows only the script's warning, not just's red "recipe failed" lines; a `dsc-set-features` or `dsc-set-system` failure is still reported by the inner just. Enabling a feature leaves `RebootPending` set, so `wsl-install` stops the run then, before any installer. gsudo's credential cache (`gsudo cache on`) isn't used: just runs each recipe line in its own process, and the cache's per-process scope hasn't been checked against that.
