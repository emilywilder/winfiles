# Optional goals

Things that would improve winfiles but that nothing needs yet. None is scheduled and none blocks an install. Each item says why it isn't done, what would make it worth doing, and where the background is recorded. Add an item when work turns one up; delete it when it's done (the doc that records the change says so) or when the reason for it goes away. Dated 2026-11-19, from the work on `feat/drop-privs`.

## Checks not made

- **Run iris through the batches.** The documents are migrated and flatten, but only `vm-quick` and `vm` have been installed this way. Worth it before the next install on iris. Background: `install.md`, "What needs a restart".
- **A restart that becomes pending after a non-restart elevated batch.** The check exists in `Invoke-Configuration.ps1` and never fired in either VM run, so it has only been read, not seen. Needs a resource that makes one pending without reporting `_restartRequired`; the optional features are the candidate, but both runs reported WSL first.
- **How many UAC prompts `just system` and `just check` give from an unelevated shell.** `just install` gives one (checked in the VM); whether gsudo prompts once or per elevated batch from a plain terminal is unchecked. Background: `install.md`, "Batches by privilege".
- **The bootstrap retry's success path.** After `0x8A15000F` it runs `winget source update` and retries once; Pester covers only the second failure, because the success path goes on to change the machine. Check it the next time a clean VM bootstrap hits the error, or force it in a VM. Cause of the error is unknown (first winget call after a checkpoint restore, 2026-11-19, gone on the next try).

## Failures that are hard to find

- **Other resources writing their failures to `run.log`.** DSC's stderr goes to the console only (capturing it would lose the progress bar), so a resource has to log for itself. `Winfiles/Wsl` and `Winfiles.WinGet/Package` do; the Scoop and file lists and the registry resources don't. Do it when one of their failures is as hard to find as the winget one was. Background: `install.md`, "What a run says".
- **A retry for `0x80071130`** ("Fast Cache data not found"), seen once from `winget dscv3 package --get` right after a portable `Kubernetes.kubectl` install, 7m07s into a `vm` user batch; a rerun passed. Cause unknown and the package whose `get` failed isn't recorded, so no retry yet. If it recurs, the `[winget]` line in `run.log` now names the package; retry there only if it keeps happening.
- **Resource-level events** at the default level (which document, which package or distribution is installing) and the full output at a `debug` level. Researched 2026-11-16 from the code and `demos/dsc-messages`, not tried. Today the default `warn` level shows only Scoop's `Installing '...'` lines, raised to `WARN`; winget, the WSL and file resources and the built-ins say nothing unless they fail (`reference/dsc.md`, "Resource messages and levels"; `reference/winget.md`). The way to try: run `set` with `-l info --trace-format json`, have `Set-Winfiles.ps1` read stderr and show only winfiles' events and DSC's "Invoking set" lines, and pass everything through at `debug`. Risks to settle first: redirecting stderr may stop the progress bar, which needs stderr to be a console; the parser has to cope with the `PID <dsc>: ` prefix; and `Invoke-Clean.ps1` clears the environment and `install.cmd` passes only `host user`, so a `debug` switch needs a route of its own. Fallback: keep the `warn` labels and have resources write to `run.log` themselves. mise isn't worth events. Worth doing when a real `install` shows which gaps get in the way. Background: `install.md`, "What a run says".

## Cheaper or tighter

- **Test fewer resources to find a restart.** Every elevated batch is tested once more before the first `set` (11s on `vm-quick`, 24s on `vm`). Testing only the resource types that can report a restart would cut it. Worth it only if the pass becomes noticeable on a bigger host.
- **Refuse a resource-level `securityContext` in a flat document run by hand.** The flattener removes the tag from its output, but a flat document written another way, with a tag on a whole-resource-tested type, would count it as a difference. Low value: nothing writes one.
- **Refuse `..` in a `configurationFile`.** DSC 3.3.0 does; the flattener resolves it, so a bad entry passes `just install` and fails by hand. Background: `flat-configuration.md`.
- **A Pester test of the restart gate.** A child process can't mock what Windows says about a pending restart, so the old in-process tests went with `Set-System.ps1`. A seam for `Test-BlockingRestartPending` would let a test set it.

## Structure

- **A shared layer of modules for `iris` and `vm`.** A document that only includes modules, with paths from `dsc/`, which both entries include in place of their 13 identical system Includes (and a home counterpart). It would also stop a module being added to `iris` and not to `vm`. `vm-quick` has its own smaller set, so it would keep its list. The layer runs from an entry but not on its own; the modules it includes stay leaves that still do. Costs: resource messages below `trace` are lost when an entry is run by hand (not in the flat copy), two layers in one entry can't share a module, and the ordering on a host's `Features` stays in the entry. Modules that include each other are ruled out, not deferred (checked 2026-11-21). Revisit once there's a third real host, or the lists drift. Background: `architecture.md`, "Structure"; `flat-configuration.md`.
- **Optional features that report `_restartRequired` from `test`.** They report nothing, so they ride along through WSL's `dependsOn` and are only caught by the pending-restart check after a batch. A resource of their own that reports it would make that explicit.
- **A shared catalogue of WSL distributions.** Each user's distributions are written out in `dsc/users/<user>@<host>/wsl.dsc.yaml`, so NixOS-WSL appears for both `emily@iris` and `emily@vm`. A parameterised module can't be included once per distribution, since names must be unique across the flattened documents; one document per distribution (`modules/home/wsl-distros/<name>.dsc.yaml`) could be included by name instead. Worth it if several users come to share distributions, or the copies drift. Background: `architecture.md`, "WSL".
- **Move entries out of `dsc/`.** DSC 3.3.0's refusal of `..` is why entries stay there. With flattening reading the files itself, the entries could move later; a separate decision.
- **Bicep in place of the YAML documents.** Since DSC 3.2, `bicep local-deploy <host>.bicepparam` drives DSC resources through `dsc-bicep-ext` (a gRPC server that ships with DSC; it's in the 3.3.0 that mise installs), with Bicep as the orchestrator. The older route, `dsc config` running `bicep build`, was removed in 3.2.0-preview.11. Bicep would bring real modules with parameters (a shared layer for `iris` and `vm`, one module per WSL distribution), `for` loops and `if` conditions that are Bicep's rather than DSC's deprecated `copy` (PowerShell/DSC#1429), per-host `.bicepparam` files, typed properties with editor support, and dependencies from references. It isn't done because:
  - **It only applies.** `bicep local-deploy` (Bicep CLI 0.49.2, `--help` read 2026-11-21) has no test, get or what-if mode, so `just check`, testing before `set` and finding the resources that report `_restartRequired` would all go.
  - **The documents would stop being DSC's.** They would no longer run under plain `dsc config test|set` or `winget configure`, which breaks the three tests in `architecture.md`, and the flat copy, batches and aggregate would have nothing to work on.
  - **One process, one privilege.** A deployment runs at one level, where winfiles splits each run into elevated and unelevated batches.
  - **Custom resources need published types.** The `Winfiles/*` resources would need Bicep types generated from their manifests and published with `bicep publish-extension` (to an OCI registry or a local package), redone on every schema change. Run-time type discovery is listed as a future improvement in bicep-types-dsc.
  - **It's experimental twice over.** Both `localDeploy` (a `bicepconfig.json` flag) and the DSC extension are experimental, with no stability date. The modules issue (PowerShell/DSC#1269) was still open. Whether DSC's progress bar, resource warnings and `restartRequired` get through Bicep's per-resource output isn't documented.
