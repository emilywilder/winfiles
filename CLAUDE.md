# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal Windows 11 configuration management (a counterpart to the user's Linux/macOS dotfiles). It's a work in progress. There is no build and no test suite. "Testing" a change means running DSC `test`/`get` against the live machine.

## Commands

Bootstrap on a fresh Windows 11 install, from an unelevated terminal in the repo:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-Winfiles.ps1 -HostName iris   # rerun after the restart just install asks for
```

`scripts/Install-Winfiles.ps1` runs under Windows PowerShell 5.1, since nothing else is installed yet, and refuses an elevated shell. `-HostName` picks the host configuration; without it, `just` uses the computer name, which a new install usually doesn't match. Each step skips what's already done:

```powershell
winget install --id Microsoft.AppInstaller --exact --source winget --accept-package-agreements   # treats 0x8A15002B, already current, as success
winget install --id jdx.mise --exact --source winget --accept-package-agreements   # unless mise is installed
$env:Path = <machine Path>;<user Path>                       # this process only, so mise is found without a new terminal
mise trust; mise install                                     # mise.toml provides just, pwsh, gsudo and DSC
mise exec -- just install <host>                             # everything below, in order; the script exits with its code
```

`--source winget` keeps winget away from the `msstore` source, which on a fresh install stops to ask you to accept its terms (and sends your region).
`--accept-package-agreements` accepts mise's licence without a prompt. winget still asks for UAC to install the Visual C++ runtime that `jdx.mise` depends on.
App Installer comes first because a new Windows image can ship one too old for the rest. With 1.26.509 (winget 1.11, seen in the test VM 2026-11-02, on an image that hadn't been through Windows Update) the WinGet module fails when elevated (`Failed to create instance: 0x800706BA`), though not unelevated, and `Microsoft.WinGet/Source` removes `msstore`, then fails to add it back. Upgrading unelevated takes no prompt, and winget 1.29 fixes both. Only the bootstrap does this, so on an old image run the bootstrap rather than `just install`.
Reloading `PATH` from the registry only changes the script's own process, which the `PATH` constraint allows. It can't help in the middle of `just install`: a process started before Scoop was installed never sees its shims.

`just install [host] [user]` defaults to the computer name and username, and fails before any change when there's no configuration for them. It runs these, in this order. Each one skips what's already done:

```powershell
gsudo --direct mise exec -- just dsc-set-features <host> wsl-install dsc-set-system <host> # `just system`: one UAC prompt, same console
                                                             #   dsc-set-features: scripts/Set-Winfiles.ps1 dsc/hosts/<host>/features.dsc.yaml
                                                             #   wsl-install: wsl --install --no-distribution; exits 3010 while a restart is pending
                                                             #   dsc-set-system: scripts/Set-Winfiles.ps1 dsc/<host>.system.dsc.yaml
mise exec -- pwsh -File ./scripts/Set-Winfiles.ps1 dsc/<user>@<host>.home.dsc.yaml   # `just home`: unelevated; installs Scoop itself first
mise exec -- pwsh -File ./scripts/Test-Winfiles.ps1 dsc/<host>.system.dsc.yaml dsc/<user>@<host>.home.dsc.yaml   # `just check`: lists what's missing; exits 1 if anything is
mise exec -- pwsh -File ./scripts/Show-PostInstall.ps1 dsc/hosts/<host>   # `just post-install`: prints what's still to do by hand
```

A step winfiles can't do goes in a YAML comment in `dsc/hosts/<host>/` that starts with `# post-install: ` and runs to the end of that block of comment lines. `just post-install` prints these, so the text lives once, beside the setting it's about. So far that's iris's Remote Desktop, which rejected the Microsoft account's password until the account had signed in with it at the sign-in screen, with "only allow Windows Hello sign-in" off for that sign-in (seen 2026-11-04; it kept working with the setting back on). `just install` runs it last, so a stop for a restart or a failed `just check` hides the notes until the run that gets through. Trade-off: nothing can tell whether a note has been done, so they print on every `just install`, even on a set-up machine; revisit if they start being ignored.

A run inherits nothing from the shell that starts it, so it's the same from any terminal. `just system`, `just home` and `just check` each go through `scripts/Invoke-Clean.ps1`, which rebuilds the environment for its own process: Windows' per-session variables are kept, everything else comes from the machine and user values in the registry (`PATH` included), and it then runs the command under `mise exec`. So `just`, `pwsh`, `gsudo` and DSC are always `mise.toml`'s, even when the run starts from plain `just install`, and only the outer `just` and the shell of that one recipe line come from the caller. Neither mise nor just can clear an environment, which is why this is a script. Trade-off: a variable set only in the calling shell, such as a proxy, doesn't reach a run; set it persistently if a run needs it. Revisit if mise or just gains a way to do this. `just dsc` isn't part of this: it's for working on the configuration by hand.

A package that fails to install doesn't stop the run: the list logs an `ERROR`, moves on and exits 0, and so does DSC, so the later lists and resources still apply. `just check` then gives `just install`, and the bootstrap, a failing exit code. Any other failure still stops the run where it happens, before `just check`. Each `set` and `check` also writes DSC's JSON results to `~/.local/state/winfiles/dsc/<time>-<set|test>-<document>.json`, which hold each resource's duration; nothing removes them. They're outside the repo because `just test-vm-copy` replaces the repo, and `just dsc` on its own doesn't write them. Trade-offs: `check` adds about 80s to the end of a run (measured on iris), for one list of what's missing; and `just system` and `just home` on their own exit 0 after a failed package, showing only the `ERROR` line, so run `just check` after them. Revisit if `check` becomes slow enough to skip, or if a failed package gets missed.

The elevated steps come first and share one gsudo call, so each run asks for UAC once, at the start, and the restart comes while someone is watching. Run on its own, `just wsl-install` elevates itself in a separate window instead. Nothing after the UAC prompt needs attention. `wsl-install` and `system` are `[no-exit-message]`, so a stop for a restart shows only the script's warning, not just's red "recipe failed" lines; a `dsc-set-features` or `dsc-set-system` failure is still reported by the inner just. Enabling a feature leaves `RebootPending` set, so `wsl-install` stops the run then, before any installer. gsudo's credential cache (`gsudo cache on`) isn't used: just runs each recipe line in its own process, and the cache's per-process scope hasn't been checked against that.

mise (per-directory tools, like direnv): `mise.toml` holds the tools for the repo, and `mise.lock` (Windows x64 only, `mise lock --platform windows-x64`) the exact version, download URL and checksum behind each, so every install gets the same tools. mise refuses an install that doesn't match the lock. `just`, `powershell` and `gsudo` stay `latest` in `mise.toml` and only move when `mise lock --bump` is run; after changing a request in `mise.toml`, run `mise lock`. Its pwsh is there because DSC needs pwsh before `modules/system/powershell.dsc.yaml` installs it: `scripts/Invoke-Dsc.ps1` runs under it, and `PowerShellScript` and the `Winfiles/*` resources are only discovered when `tryWhich('pwsh')` finds it. Inside the repo (under `mise exec` or `mise activate`) `pwsh` is mise's, not the winget one.

DSC also comes from `mise.toml`: the GitHub release, pinned (currently 3.3.0) because this file documents version-specific behaviour. Before bumping it, re-check that behaviour and re-time `just check`, and rerun `just dsc-messages` (see `tests/dsc-messages/README.md`). Its `postinstall` deletes DSC's two discovery extensions (`Microsoft.Windows.Appx/Discover` and `Microsoft.PowerShell/Discover`), because DSC's settings have no switch for them: `dsc.settings.json` only covers `resourcePath` and `tracing`. The hook only runs when a version is installed, so after changing it run `mise install --force github:PowerShell/DSC`. `scripts/Invoke-Dsc.ps1` warns when the extensions are back.

Using mise's DSC rather than the Store package is a trade-off, not a rule. It was measured on 2026-10-28; reconsider it when either version changes:

- **Speed:** with the extensions, each `dsc` process spent about 0.8s in the PowerShell one, which found nothing, and about 2.5s in the Appx one. Every Include starts another `dsc` process, so this repeats. A whole-composition `test` took about 34s under mise's 3.3.0 without extensions, about 41s under the Store 3.2.3, and about 91s under 3.3.0 with them.
- **Maintenance:** there is one way to install DSC, with no Store install script, second mise environment or duplicate `*-github` recipes. The version is pinned in the repo instead of updated by the Store. The Store package's `dism_dsc` also refuses to run ("not supported when installed via Appx").
- **Clarity:** only one version needs documenting. With the extensions, a run could also mix in resources from another installed DSC: the Appx extension found the Store DSC's own `Include`, `PowerShellScript` and `Registry`.
- **Cost:** resources that exist only inside Store packages aren't discovered, so `just dsc-export` no longer exports `OhMyPosh/*`. winfiles' documents use none of them, and export is a nice-to-have of uncertain use, outside the project's main focus, so this weighs little. A machine may still have the Store DSC (`9NVTPZWRC6KQ`) installed. It isn't on `DSC_RESOURCE_PATH`, and under `mise exec` mise's `dsc` comes first on `PATH`.

DSC (v3, `dsc` CLI). Run it through `just dsc` (`scripts/Invoke-Dsc.ps1`), which passes arguments to `dsc` after setting `DSC_RESOURCE_PATH` for that process only. The path covers DSC's install folder, App Installer's (`Microsoft.WinGet/*`) and `dsc/resources` (the `Winfiles/*` resources). This is how `Winfiles/*` resources are found, and it stops every `dsc` process from scanning all of `PATH` for manifests. `tryWhich` conditions, such as `pwsh` and `sshd`, still search `PATH`. `just dsc-export` (`scripts/Export-DscResource.ps1`) runs `dsc` the same way. It writes the current state of every exportable resource to `exports/`. It's a nice-to-have, not part of applying the configuration, so don't let it drive design decisions:

```powershell
just check [host] [user]                                     # both configurations; lists what's missing and exits 1 if anything is
just dsc config test --file dsc/iris.system.dsc.yaml         # one configuration, as full JSON (or dsc/emily@iris.home.dsc.yaml)
just dsc config test --file dsc/modules/system/policies.dsc.yaml   # one module on its own
just dsc config get  --file <doc>                            # current state
just dsc config set  --file <doc>                            # apply (HKLM resources need an elevated shell)
```

`dsc config test` exits 0 whatever it finds, so a script has to read its results, not its exit code; `scripts/Test-Winfiles.ps1` does that for `just check`. Run `test` before `set` and check the result. `set` changes the real machine: it installs packages, writes the registry, and rewrites profile stubs (keeping `.bak` copies).

just (recipes are `[windows]` only and run in pwsh, without the profile, which cost about 5s per recipe line on iris against 0.47s; a recipe that comes to need something from the profile has to set it up itself):

```powershell
just                  # list recipes
just install [host] [user]   # clean install to a host's system and home configurations (see above)
just system [host]           # apply the system configuration (elevates)
just home [user] [host]      # apply the home configuration (unelevated)
just check [host] [user]     # test both configurations; exits 1 if anything is missing
just post-install [host]     # show what a host still needs done by hand after an install
just hosts                   # list the configurations in dsc/
just manual [host]           # download the installers of what a host installs by hand and is missing
just wsl-install      # install WSL (scripts/Install-Wsl.ps1); skips if it's already set up
just test-vm <iso>    # Hyper-V VM with nested virtualization for testing `just install` (scripts/New-TestVm.ps1); skips if it exists
just test-vm <iso> -Unattended   # the same, with Windows already applied and OOBE answered
just test-vm-copy [name]          # copy the working tree into a running test VM's ~\src\winfiles (scripts/Copy-RepoToTestVm.ps1)
just test-vm-shell [name]         # PowerShell Direct session in a running test VM (scripts/Enter-TestVm.ps1)
just test-vm-run <name> <command> # run one command there, in ~\src\winfiles, and pass on its exit code
just dsc-messages <doc> [dsc args]   # watch how dsc shows resource messages, using dummy documents in tests/dsc-messages
```

`tests/dsc-messages/` is a visual check, run by hand, of how DSC shows lines a resource writes to stderr (levels, live output, Include nesting). Its README records the results per DSC version. Its stand-in resource `Test/SlowList` is outside `dsc/resources`, so `just dsc` never discovers it.

A test VM's computer name doesn't decide its configuration, so pass the host: `just install vm`, or `-HostName vm` to the bootstrap. Test a clean install in that VM, not in Windows Sandbox: the Sandbox doesn't expose virtualization to its guest, so WSL2 can't run there, and it has no Store or winget. The script creates the VM and doesn't start it. It fixes the screen at 1920×1080 for basic `vmconnect` sessions (the VM's own console); an enhanced session (Remote Desktop over VMBus, with a shared clipboard) sizes it to the window. It prints the `Checkpoint-VM` and `Restore-VMCheckpoint` commands for taking a `clean` checkpoint after Windows setup and returning to it. Without `-Unattended` the VM boots the ISO into Windows Setup. With it, Setup is skipped: the script applies `Windows 11 Pro` from the ISO to the VHDX, runs `bcdboot`, and writes `Windows\Panther\unattend.xml`, which answers OOBE, creates a local administrator named after you, and signs it in automatically at every boot, so the bootstrap's restart needs no attention. The administrator's password is blank, and the specialize pass sets `LimitBlankPasswordUse` to 0, which by default limits blank passwords to the console. So a basic session opens on the desktop, an enhanced session signs in with one click on **Sign in**, and PowerShell Direct needs no password; a restart comes back by itself in either session (checked 2026-10-29 on 26300). The VM's notes record the administrator (`Local administrator: <user> / `, with nothing after the slash), and `scripts/testvm.ps1` reads them for the PowerShell Direct scripts. Trade-off: a blank-password administrator that accepts remote sign-ins, acceptable only because the VM is a throwaway behind the Default Switch's NAT; never do this on a real machine. It replaced a generated password kept in the notes, which every sign-in through an enhanced session made you type. The VM has no sleep states (`powercfg /a`), so it never asks to sign in on wake. The computer name defaults to the VM name, and Setup rejects one longer than 15 characters at first boot, so the script checks it up front; pass `-ComputerName` for a longer `-Name`. The VM stays unactivated, which doesn't affect winfiles.
`just test-vm-copy` packs the repo with `git archive` (by default the working tree: commits plus uncommitted changes to tracked files, through `git stash create`; untracked files are left out) and copies it in over PowerShell Direct, signing in with the administrator from the VM's notes (`-Credential` for a VM installed by hand). It replaces `~\src\winfiles` in the VM, so edits made inside the VM are lost.
PowerShell Direct sessions run elevated with no UAC, so run the bootstrap in the VM's desktop, and keep `test-vm-shell` and `test-vm-run` for reading results, such as `just test-vm-run <name> 'mise exec -- just check vm'`. Under them, Scoop's installer would refuse to run and the gsudo prompt would never show.

## Architecture

The state is described with DSC v3, and the root `justfile` drives it. The earlier just modules, exported winget/Scoop package lists and monolithic `modules.dsc.yml` were removed; git history has them.

- **Structure, modelled on NixOS and Home Manager (see nix-starter-configs):** each configuration is an entry document directly in `dsc/`, split by the privileges `set` needs. `<host>.system.dsc.yaml` is like `nixosConfigurations.<host>`: it needs an elevated shell, and `just system` applies it. `<user>@<host>.home.dsc.yaml` is like a standalone `homeConfigurations."<user>@<host>"`: it runs unelevated, and `just home` applies it. Entries only list Includes. Reusable documents go in `dsc/modules/system` and `dsc/modules/home`, and one machine's differences go in `dsc/hosts/<host>/`. `just install` applies system then home, so ordering between them lives in the justfile, while `dependsOn` orders Includes inside an entry. A `dependsOn` can't cross from one to the other. The hosts are `iris` and `vm`, for test VMs, which has every shared module and none of a real machine's hardware. To add a host, create `dsc/hosts/<host>/` and copy a pair of entries, then edit their module lists.
  `configurationFile` paths resolve relative to the folder of the top-level document (the one passed to `--file`), so a configuration works from any working directory. In DSC 3.3.0 (and 3.2.3) this also applies to nested Includes. DSC 3.3.0 also refuses `..` in these paths, so entries have to stay directly in `dsc/`, above what they include. Modules don't include each other, so each one also runs on its own, and entries state the ordering.
  Trade-off: each entry repeats its module list, where Nix would import a common file. A shared layer of Includes works, but two levels of Include lose every resource message below `trace` (`tests/dsc-messages/README.md`). Revisit once there's a third real host or that DSC bug is fixed.
  Modules hold nothing specific to one person or machine, so the project can become a starting point for others later: per-machine differences go in `dsc/hosts/` or an entry. A document that needs elevation for any of its resources goes in `modules/system`. `dsc/templates/` is reference material and is deliberately left out of the configurations.
- **Optional features:** `dsc/hosts/<host>/features.dsc.yaml` holds the Windows optional features a host relies on (Virtual Machine Platform, plus Hyper-V on iris, which hosts the test VMs), in one `Microsoft.Windows/OptionalFeatureList`. Add new features there. DISM doesn't enable a feature's children along with it, so each one is listed, parents first. The resource needs elevation even for `get`, and DSC then refuses the whole run, so the document is left out of the entries, which keeps their `test` unelevated. `just system` sets it on its own, first among the elevated steps. Check it with `just dsc config test --file dsc/hosts/iris/features.dsc.yaml` from an elevated shell. Trade-off: `just check` doesn't cover features. A custom resource reading `Win32_OptionalFeature` over CIM (unelevated, as `wsldistribution.ps1` does) would bring them back in, at the cost of a script to maintain; revisit if features drift unnoticed.
- **Packages:** each feature (base, dev, gaming, internet, productivity, media) has a document with the same name in `dsc/modules/system` and `dsc/modules/home`, and each holds at most one `Winfiles/WinGetPackageList` and one `Winfiles/ScoopPackageList`. `modules/system/runtimes.dsc.yaml` holds the shared runtimes, and `dsc/hosts/<host>/hardware.dsc.yaml` and `home.dsc.yaml` hold what only one machine wants. MSIX frameworks (VCLibs, UI.Xaml, .NET Native, Windows App Runtime) are left out unless an app needs them listed, since the image and the Store supply most of them. Trade-off: `Install-WinGetPackage` fails installing UI.Xaml 2.6 as a dependency (`0x8A150110` on winget 1.29.380, checked 2026-11-03 in the test VM), though the `winget` CLI manages it, so that one id is listed just before ChromaControl, which declares it. It's the only dependency install through the cmdlet that has been seen, so a new app with a missing dependency may fail the same way; list the dependency first if so. Revisit when winget updates. Comments inside each list group the packages by purpose. Each resource checks its list with a single listing of installed packages, and it only installs: removing an id doesn't uninstall the package. Before each install, `Winfiles/WinGetPackageList` prints `Installing <id> (3/8)`, labelled `WARN`, because that's the lowest level DSC shows by default; a slow download otherwise looks like a hang. A package that fails stays in the list's `missing` property, and the list still exits 0, because DSC stops the whole configuration when a resource exits non-zero. To add a package, add its id under the right comment: in `modules/home` if it has a per-user installer (`winget show --id <id> --exact --scope user` names one) that really runs unelevated, otherwise in `modules/system`. Home lists set `scope: User`, which makes winget pick a per-user installer; a package with no such installer fails instead. The manifest doesn't prove the installer needs no elevation: KDE Connect's `Scope: user` installer, run with `/S /CurrentUser`, still raises a UAC prompt and waits for it, so it's in `modules/system`. Only a run in the test VM shows this. Scope only applies when installing, and a package already installed counts whichever way it was installed. Trade-off: each list costs about 1.75s in `test`, and modules took winget from 8 lists to 15, for a clear place for each package. Revisit if `test` gets slow enough to discourage running it. A package that needs per-package options (`version`, `useLatest`) has to be a `Microsoft.WinGet/Package` resource instead. Packages that are managed elsewhere are left out: PowerShell (`modules/system/powershell.dsc.yaml`), DSC itself (`mise.toml`), WSL (`scripts/Install-Wsl.ps1`), IntelliJ IDEA (JetBrains Toolbox), Python and Meld (Scoop, in `modules/home/dev.dsc.yaml`), Discord (Scoop, in `modules/home/internet.dsc.yaml`: winget's installer starts Discord, which asks for UAC mid-run), and whatever is installed by hand (see below). `modules/system/settings.dsc.yaml` also marks the `msstore` source explicit (`Microsoft.WinGet/Source`), so winget only uses it when a command passes `--source msstore`. The bootstrap still passes `--source winget`, since it runs before DSC.
- **Installed by hand:** `dsc/hosts/<host>/manual.yaml` lists what a host needs that can't be installed unattended, each with why. So far that's iCUE, Battle.net and LyX on iris. The TeX engine is Tectonic, from Scoop in `modules/home/productivity.dsc.yaml`. It has no `latex.exe`, which LyX's installer looks for, but LyX can be made to work with it (tested on iris with TeX Live moved out of the way, 2026-11-03). Trade-off: a small engine that winfiles can install unattended, rather than a full distribution it can't. Revisit if something needs a full LaTeX distribution. `just manual [host]` (`scripts/Get-ManualInstaller.ps1`) finds what's missing from the display names in the Uninstall registry keys, downloads it to `~/.cache/winfiles/manual` with `winget download`, which checks the manifest's hash, and never runs an installer. It's outside DSC, so `just check` still means what winfiles can apply by itself, and a host with no list has nothing to do, like `vm`. An entry can move to an ordinary list if its installer turns out to work unattended. PowerShell has no YAML parser, so the list is read with `yq` from `mise.toml`. Trade-off: one more tool in every bootstrap, for a list in the same format as everything else in `dsc/`. Revisit if `yq` is ever the only reason something breaks. The list goes with the host rather than the module because what a machine wants installed by hand differs, but LyX and Battle.net would otherwise belong to shared modules, so a new host has to copy those entries.
- **Scoop:** `Winfiles/ScoopPackageList` follows the same pattern. Entries are `name` or `bucket/name`. `dsc/modules/home/scoop-core.dsc.yaml` declares every bucket (name → repository URL) in one list with no apps, so other modules only list apps and depend on it in the entry. State comes from reading `apps/<name>/current/scoop-install.json` (`install.json` from older Scoop versions) and `buckets/<name>` under the Scoop root, not from running Scoop. `set` adds missing buckets, then makes one `scoop install` call for the missing apps. Scoop's own `Installing '<app>' ...` lines are raised to `WARN`, for the same reason as winget's, and an app or bucket that fails stays in `missing` or `missingBuckets` with the list still exiting 0. `Core` installs git with no buckets, and `Buckets` depends on it, because adding any bucket other than `main` needs git. Scoop finds git through its shims, so before calling Scoop the list puts `<root>\shims` on `PATH` for its own process: the `dsc` process of a fresh `just install` started before Scoop's installer added them to the user `PATH`. Scoop itself is installed by a separate resource, `Winfiles/Scoop`, the first in that document. `Core` depends on it, and the other modules follow through the entry. Its `set` downloads and runs Scoop's own installer, and its only job is installing Scoop; buckets and apps stay with `Winfiles/ScoopPackageList`. The installer refuses an elevated shell, so the resource's `set` exits with 3 there instead of trying. That's why Scoop is in a home configuration. If Scoop is still missing when a list's `set` runs, that list exits with 3 too. Both resources look up the Scoop root with `Get-ScoopRoot` from `dsc/resources/scooproot.ps1` (`$env:SCOOP`, then `root_path` in Scoop's config, then `~\scoop`), which their scripts dot-source.
- **WSL:** `dsc/modules/home/wsl.dsc.yaml` writes `~/.wslconfig` and `~/.wslgconfig` from inline content (`Winfiles/FileContentList`, since there's no built-in file resource; the content starts with a `Managed by winfiles` comment because DSC parses a string starting with `[` as an expression). It also installs NixOS-WSL with `Winfiles/WslDistribution` and makes it the default. It does only the Windows side: everything inside the distro (`wsl.*` options, `/etc/wsl.conf`, users) belongs to the NixOS configuration. The resource reads state from the `HKCU\...\Lxss` registration, never unregisters or moves a distribution, and `location` only applies at install time. WSL itself is installed before DSC runs, by `just wsl-install` (`scripts/Install-Wsl.ps1`). It runs `wsl --install --no-distribution`, which installs the WSL package and also enables VirtualMachinePlatform. The winget `Microsoft.WSL` package doesn't enable the feature. In `just install`, `features.dsc.yaml` has already enabled it, and the script enables it too so it also works on its own. The script skips when WSL is already set up and elevates through UAC otherwise. Before installing a distribution, the resource checks through CIM that the feature is enabled and that WSL is 2.4.4 or later, and that no restart is pending, and exits with 3 if not. The script uses the same check, so keep the two in step.
  `dsc/modules/system/wsl.dsc.yaml`, in the system configuration because setting it needs elevation, limits inbound access to WSL to SSH into NixOS from the local network. With mirrored networking, inbound traffic to WSL goes through the Hyper-V firewall, per VM creator (WSL's is `{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}`), with host rules that have no program merged in. WSL doesn't register its creator when it's installed or when its service starts (checked on WSL 3.0.3, in a test VM without Hyper-V), so on a new install the document creates the setting itself. The document sets WSL's default inbound action to Block, on the creator and each of its profiles, and declares one Hyper-V rule: TCP 2122 (NixOS's sshd port, set in the NixOS configuration), Private profile, `LocalSubnet`. Another service in NixOS that should be reachable from the network needs its own rule there. `Microsoft.Windows/FirewallRuleList` only manages host rules, so it's done with the NetSecurity cmdlets; reading them needs no elevation, so `test` stays unelevated.
  The pending restart is read from `Component Based Servicing\RebootPending`: right after `wsl --install`, before any restart, the feature already reads as enabled (CIM `InstallState` 1, `RestartNeeded` false on build 26300). The script exits with 3010 whenever that key is set, including after installing and when WSL is already set up, so `just install` stops before DSC. `mise exec` cuts an exit code to its low byte, so anything running the script under it, `just system` and the bootstrap included, reports 194 rather than 3010; any non-zero code stops the run, so this does no harm. Trade-off: the key also covers Windows Update, so `just install` stops for a restart Windows Update is waiting on, even on a set-up machine. Installers such as `Microsoft.DotNet.Framework.DeveloperPack.4.6` refuse to run then anyway ("RebootPending = 0" bundle condition, seen in the test VM 2026-10-29). Revisit if that stops become a nuisance.
  When the script has just installed WSL and the key is set, it runs `Restart-Computer` after a 30-second warning, then still exits with 3010 so DSC doesn't start during the shutdown. With WSL already set up it only warns, because `just system` runs on working machines, where a restart could come from Windows Update and take open work with it. There's no `-Force`, so an app with unsaved work can still stop the restart. Trade-off: the restart closes the terminal, so rerunning `just install` afterwards is on you, and the warning is the only reminder. Revisit if that gets missed; continuing by itself would need something like a `RunOnce` entry.
  `just wsl-install` runs the script under mise's pwsh 7, like every other recipe. It used to run under Windows PowerShell 5.1 so it would work before pwsh was installed, but the bootstrap now runs `mise install` first. 5.1 turned `wsl.exe`'s "not installed" on stderr into a fatal error, and this way the bootstrap recipes are less of a special case. The script keeps `#Requires -Version 5.1` and 5.1-compatible syntax, so it still runs by hand on a bare machine. Revisit if the bootstrap ever has to run before mise.
- **Custom resources:** these live in `dsc/resources/` as `*.dsc.resource.json` manifests plus scripts. `just dsc` makes them discoverable. Each script dot-sources `common.ps1`, which sets the preferences and provides `Read-ResourceInput` and `Write-ResourceMessage`. The scripts have no `[CmdletBinding()]` or `[Parameter()]`, so `$input` can hold the JSON from stdin. DSC logs plain stderr lines at `trace` only, so a failure has to go through `Write-ResourceMessage error`, and each script's `trap` does that for uncaught errors; it has to be in the script, because a trap only covers the scope that declares it, even when dot-sourced. Output from Scoop and `wsl.exe` stays plain, so see it with `-l trace`. Trade-off: a failure names the package but not the tool's own explanation, which keeps a normal run readable; revisit if failures keep needing `trace`.
  `Winfiles/FileContentList` writes whole text files from inline content, keeping a `.bak` of a file it replaces. `specialFolder` is for folders that can be redirected, such as `MyDocuments` (OneDrive on this machine), which `%USERPROFILE%` can't reach.

DSC document conventions (copy them from existing documents):

- Each document has the `$schema` (2023/08 document.json) and `metadata.winget.processor.identifier: dscv3` header, which keeps it usable with `winget configure`.
- Configurable paths and keys go in `parameters` with a `defaultValue`. Paths are stored with `%VAR%` placeholders and expanded inside scripts with `[Environment]::ExpandEnvironmentVariables`.
- Each resource has a `metadata.description`, except `Microsoft.Windows/RegistryList`, which gets a comment instead: DSC 3.3.0 passes the description to the resource as `_metadata`, which the list's synthetic test counts as a difference, so `test` would always report false and every `set` would rewrite the values. Ordering is set with `dependsOn: "[resourceId('<type>', '<name>')]"`.
- Several registry values in a document go in one `Microsoft.Windows/RegistryList`, which also creates their keys. Trade-off: a drifted value reports the whole list as false with `differingProperties: registryEntries`, so finding which one means reading `actualState`; revisit if that gets in the way.
- Prefer DSC built-in resources (`Microsoft.Windows/Registry`, `Microsoft.WinGet/Package`, `Microsoft.DSC/Include`, ...) over scripts. Use `Microsoft.DSC.Transitional/PowerShellScript` only when no built-in can do the job, or one is broken. In that case, add a comment saying which built-in was ruled out and why. Pass the script's data through `input`, and make `getScript`/`testScript`/`setScript` idempotent (`testScript` returns a bool).

How PowerShell is set up (this is the non-obvious part). `dsc/modules/system/powershell.dsc.yaml` installs PowerShell and `Microsoft.WinGet.Client`, and `dsc/modules/home/powershell.dsc.yaml` does the rest:

- PowerShell's CurrentUser install scope always writes to `Documents\PowerShell\{Modules,Scripts}`. The document points `PSModulePath` (in `powershell.config.json`) at `~/.local/share/powershell/Modules` and replaces both Documents folders with junctions to `~/.local/share/powershell/{Modules,Scripts}`, migrating existing contents and keeping clashes in `.bak` folders.
- With the junctions, the `PSModulePath` setting is redundant in effect. It's kept as a trade-off: `Documents` is redirected to OneDrive on this machine, and the setting keeps module loading off the junction inside it, so only installs go through it. The cost is that if the junction goes missing, CurrentUser installs land outside `PSModulePath`. Revisit if `Documents` stops being redirected (checked 2026-10-28).
- Modules are installed with `Save-PSResource` into that path, not through `PSResourceList`. The junction would make `PSResourceList` usable now, but PSResourceGet 1.2.0 (shipped with PowerShell 7.6.9) has no DSC manifest for it, and a version that has one would also need its folder on `DSC_RESOURCE_PATH`. `Save-PSResource -Path` doesn't depend on the junction existing.
- `Microsoft.WinGet.Client` goes in `%ProgramFiles%\PowerShell\Modules` instead, because the system configuration's winget lists need it before any home configuration has run. That folder stays on `PSModulePath` for every pwsh 7, mise's included, whatever the user setting says. A copy already in the user module path loads first, which is harmless.
- `$PROFILE` can't be relocated, so the default profile files become stubs (they start with `# Managed by winfiles (...)`) that repoint `$PROFILE` and dot-source `~/.config/powershell/`. They're written by `Winfiles/FileContentList`, which ignores line endings and trailing whitespace when comparing, so any other edit to a stub makes `test` report false until the next `set`.
- `Microsoft.PowerShell/Profile` is avoided because its `get` is broken (`JSON: EOF while parsing a value`). It ships with PowerShell, not DSC, and fails under both DSC 3.2.3 and 3.3.0.

## Constraints

- winfiles must never modify the persistent `PATH`. The pwsh profile (kept outside this repo) owns `PATH`, including the junctioned Scripts folder. Changing `PATH` for a single process inside a recipe is fine. A tool that winfiles drives may change the persistent `PATH` only if the user has approved that tool. So far Scoop (its installer, and manifests with `env_add_path` such as nodejs and python) and winget (package installs and uninstalls) are approved. Ask before relying on any other tool doing it.
- Commit messages use conventional commits plus gitmoji, scoped by area, for example `feat(dsc): ✨  ...`, `refactor(dsc): ♻️  ...`, `chore: 📝  ...`. Put two spaces after the gitmoji: terminals draw emoji such as the recycling symbol wider than the cell they reserve, which hides a single space.
